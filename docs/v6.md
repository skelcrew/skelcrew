# Skelcrew v6

Nov 17, 2026 · design, not yet built · `docs/spec.md` still describes what Skelcrew does today, and is updated phase by phase as this lands

## Why

Skelcrew today is half a multiplexer. It runs its own split-screen terminal app, with a second tmux server, a sidebar, tabs, lists, pages and a footer. That part has grown into the biggest and most fragile part of the code, and it competes with tools that do nothing else.

v6 makes Skelcrew thinner and easier to combine with other tools. It becomes closer to a workflow manager: Docker for running agents.

- The repository describes how its agents work, in files, as a `Dockerfile` or `package.json` does. Skelcrew is the engine that runs what the files say.
- Agents run in a session host. tmux is the default. A session plugin can bring another, such as herdr-core (`hc`, https://github.com/herdrdev/herdr-core), and later Rex. With herdr, its desktop and mobile apps show Skelcrew's leads and builders and let you chat with them. No host is the main one: tmux and Skelcrew's own list are the default, and plugins make the others possible.
- Issues, threads and PRs stop being three objects. Skelcrew keeps tasks, and each task has threads.
- The command line works like npm's.
- The screen becomes a simple list, a picker rather than a layout.

## What stays

Most of Skelcrew stays as `docs/spec.md` describes it. Agents still work the same way: a lead, builders in sandboxes, an adversarial reviewer, and you merging. But v6 does change how some of that work runs, not only how it is shown, and **What changes** lists every such change.

- **The lead.** One per repository, on your harness, always running, seeing only its repository. It proposes, you say yes, it starts work.
- **The sandbox.** bubblewrap on Linux and `sandbox-exec` on a Mac, drawing the same boundary. A thread's own clone and branch. No tokens inside. Agents never call GitHub. Every trap in `docs/learnings.md` still applies.
- **The harness modules.** Claude Code and Codex, one module each, with their hooks (`Stop`, `StopFailure`, Codex's `Interrupt`) and their logins. Harnesses are still never plugins, since the module draws the sandbox boundary.
- **Tracker and forge plugins.** The manifest, the jobs, the `call` questions and answers, the GitHub plugin, Skelcrew's GitHub App and its service. Only how a plugin is installed changes.
- **The build ⇄ review loop.** A builder submits with `sc submit`. A fresh reviewer, on another model if you choose, reviews adversarially and answers in a fixed shape. Changes go back to the builder. The round limit, the review queue and `limits.reviews` stay.
- **CI and the PR's events.** Failed checks, people's comments, merge conflicts and merges wake the builder or end the work, as the events table in the spec says.
- **Needs you.** The same reasons, from the same hooks, told to the lead the same way.
- **The daemon.** One per machine. Agents keep running through its restart, and it reconnects to them, resumes their conversations, and reruns reviews cut short.
- **`--remote`.** Over plain `ssh -t`, with the version kept in step with the laptop. It gets thinner, as **Remote machines** says.
- **Messages.** `sc tell` between the lead and a builder, in `<skelcrew>` tags, and the lead's messages as changes to the task that the reviewer sees. The rules stay. They move into a module of their own, as **Messages** says.

## What changes

| Today | v6 |
| --- | --- |
| Issues, threads and PRs, three objects | Tasks, each with threads, an optional issue and one PR |
| Skelcrew keeps no tasks of its own | Skelcrew keeps tasks. The tracker is a source and a mirror |
| A thread is the work on a task | A thread is one agent working on a task, in a role |
| Roles and prompts are in the code | Roles, flows and skills are files in `.agents/`, with built-in defaults |
| `skelcrew.yaml` holds setup, test, harnesses and models | `skelcrew.yaml` holds the repository's setup. Roles hold harnesses and models |
| `sc plugin install`, the first run, `sc serve`, copying the laptop's setup to a server | `sc install`, `sc add`, `sc remove`, `sc update`, `sc up`, `sc --remote <host> install` |
| Plugins installed at their newest tag | Plugins locked to an exact version in `skelcrew.lock` |
| Agents run on Skelcrew's tmux server | Agents run in a session host: tmux, or a session plugin |
| An agent's state shows only on Skelcrew's screen, read partly from hooks and partly from the screen | An agent's state is kept on its thread, from hooks where a hook fires and from the screen where none does, and reported to the session host |
| A thread ends only when its PR merges or closes, or you remove it | Unchanged. Closing an issue by hand still ends nothing |
| `limits` is only ever yours | `skelcrew.yaml` can set `limits.threads`, how many builders run at once in the repository |
| A repository you can push to runs its files without a question | A repository's `.agents/` runs only once you approved it, the first time and after each change |
| A split-screen terminal app | A list you pick from, which attaches full screen |
| `sc remote add`, and your setup copied to the server before every `sc --remote` | `sc --remote <host> install` and `sc --remote <host> up --bg`. Seeing agents from elsewhere is the session host's job |
| Messages typed in by code spread across the flow | A messages module in core, on a transport the session host provides |

## Words

| Word | Meaning |
| --- | --- |
| Lead | Unchanged: your agent session for one repository, on your harness, always running. You talk to it. It proposes tasks and starts them once you say yes. |
| Repository | Unchanged: a git repository Skelcrew works on, from a clone of its own. |
| Task | What you want done, kept by Skelcrew: its title, description, flow, stage, the lead's updates, and links to the issue it came from and the PR it produced. One task makes at most one PR. |
| Issue | An item in a tracker, such as a GitHub issue or a Linear ticket. An issue can become a task. A task needs no issue. |
| Stage | Where a task is: `issue`, `working`, `ready for review`, `merged` or `closed`. |
| Flow | The stages a task goes through and their settings, such as the round limit and the reviewer's role. A file in `.agents/flows/`. |
| Role | What an agent does on a task: its instructions, harness and model. `lead`, `builder` and `reviewer` come built in. A flow can name others. A file in `.agents/roles/`. |
| Thread | One agent working on a task, in one role, on one harness, in one session. A task usually has one thread, its builder. |
| Builder | The role that writes the change. Its thread lives from the task's start until its PR merges or closes. |
| Reviewer | The role that reviews each round, fresh each time. In v6 it runs once per round and has no thread. |
| Round | One submit and the review of it. |
| Event | Something that happened to a task: a review, a PR comment, a failed check, a merge. |
| Needs you | A flag on a thread, shown on its task: a question, a stop without submitting, a harness error, the round limit, a failed review. A task in `ready for review` waits on you too, by its stage. |
| Skill | Knowledge an agent loads when it needs it, as a folder with a `SKILL.md`. A folder in `.agents/skills/`. |
| Session host | What runs agents' sessions and lets you attach to them: tmux, or a session plugin such as herdr. |
| Plugin | A program in a repository of its own that does one or more jobs: tracker, forge, chat, machine, and now session. |
| Lock file | `skelcrew.lock`: the exact version and commit of every plugin a repository uses. |

Tracker items are called issues everywhere: in commands, in the list and in the lead's words. The word task means Skelcrew's own object only.

## Tasks and threads

### Tasks

A task is Skelcrew's own record of a piece of work, from the first words to the merge. It has:

- a **name**, such as `app-12` or `app-t3`;
- a **title** and a **description**, which the builder gets as its first message;
- a **flow**, named when it starts, `default` unless said otherwise;
- a **stage**: `issue`, `working`, `ready for review`, `merged` or `closed`;
- the **lead's updates**: every message the lead typed into one of its threads after it started, in order, with who sent it and when. The reviewer gets them after the description, as it does today, under "Changes to the task from the lead, after the thread started";
- a link to the **issue** it came from, if it came from one;
- a link to the **PR** it produced, once there is one, with its CI state and Skelcrew's review state: the round, the reviewer, the verdict.

The stages mean:

| Stage | When |
| --- | --- |
| `issue` | An open issue that no thread has worked on yet. A task with no issue never has this stage: it starts in `working`. |
| `working` | Agents are on it: the builder works, a review runs, CI runs, or a thread needs you. A task whose thread stopped or failed stays here too, so it doesn't vanish. |
| `ready for review` | Skelcrew's reviewer approved the latest round and CI is green. It waits for the human: you review and merge. Without a forge, the branch is approved and waits for you. |
| `merged` | The PR merged, or without a forge, the branch's changes reached the default branch. |
| `closed` | The work ended without a merge, by `sc rm` or a PR closed without merging, and there is no open issue behind it. Or its issue closed while it was still in stage `issue`. |

`merged` and `closed` are the end. The list doesn't show them, and `sc ls --all` does.

When the work on a task ends without a merge and its issue is still open, the task goes back to stage `issue`, not to `closed`. That is today's behaviour told as a stage: after `sc rm app-12`, issue #12 shows as not started again. It is the same task, with the same name. Its threads, its closed PR and the lead's updates stay in its log, and `sc show app-12` lists them as an earlier attempt under the issue. `sc start app-12` starts the same task again, from the issue's title and body as they are then, in a fresh clone on a fresh branch, with no updates carried over, as `sc start` after `sc rm` does today. A task with no issue, such as `app-t3`, goes to `closed`, and `sc start app-t3` starts the same task again from its own title and description.

Needs you stays a flag on a thread, never a stage. A task in `working` can need you, and the list shows why in its row.

### Names

A task has one name, used everywhere. It is the issue's ID with the repository's short name in front when the ID doesn't name a repository, as today: GitHub issue #12 in app is `app-12`, and Linear's `JOTT-12` stays `JOTT-12`. A task with no issue gets a `t` and a number of Skelcrew's: `app-t3`. A task never gets a second name, so the name in Skelcrew is always the one in the tracker.

A thread is addressed as its task and its role: `app-12/builder`. Wherever a command takes a thread, the task's name alone means its active thread: the one that needs you, or else its builder. So `sc attach app-12` and `sc tell app-12 "…"` work as they do today. The slash never needs quoting in a shell.

### Threads

A thread is one agent on a task. It has:

- its **role**, such as `builder`, or one a flow defines;
- its **harness** and **model**, from the role, kept for the thread's life, since a conversation can't move between harnesses;
- its **session**: the session host it runs on and the session's ID there;
- its **state**: `working`, `idle`, `asking` or `error`, from Skelcrew's hooks, and its status as today: `working`, `waiting`, `failed`, `stopped` or `done`;
- its **needs you** reasons;
- for a builder, the task's **branch and clone**, which the builder owns.

Today's thread becomes a task with one builder thread. Everything that belongs to the work rather than the agent moves to the task: the title, description, short title, the lead's updates, the PR, CI, the round count and the review state, and whether Skelcrew assigned you the issue.

### One PR per task

A task makes at most one PR, from its builder's branch. Work that needs two PRs is two tasks, and the lead says which comes first with `sc tell`, as today. This keeps the stage of a task as plain as the state of one PR. Whether a task should ever hold several PRs, such as one per repository, is an open question at the end.

### Reviewers

Reviewers stay one-off runs in v6: a fresh agent for each round, with no session and no thread, as today. A review is recorded on the task, as part of its review state.

They could become threads later. A flow would say `review: { role: reviewer, keep: true }`, and the reviewer would be `app-12/reviewer`, with a session of its own. Each round's diff would be typed into that session, so the reviewer remembers what it asked for, and you could attach to it and ask why. The cost is the fresh view: a reviewer that remembers its last round can come to share the builder's blind spots. So it stays a choice for later, and the default stays fresh.

### The tracker is a source and a mirror

Today the spec says Skelcrew keeps no tasks of its own: you plan in the tracker, and Skelcrew follows it. v6 reverses this. Skelcrew keeps tasks, and the tracker is where many of them come from and where Skelcrew shows how they are going.

The reasons:

- Skelcrew already keeps tasks, in hiding. A thread with no issue keeps its title and body, and the lead's updates change every task after it starts, in Skelcrew only. So what the reviewer checks against was never just the issue.
- A task's life spans the issue, the agents and the PR. With three objects, every reader joins them again: the sidebar's three lists, `sc ps`, the strip. One object with a stage is simpler to show and to reason about.
- A flow, a stage and the lead's updates need a home that every tracker has, including no tracker at all.
- Trackers differ. Linear, Jira and GitHub each have their own states. Skelcrew's stages stay the same whichever one a repository uses.

What stays true: you still plan where you already do. An issue on GitHub still shows up in Skelcrew with nothing to write, and the `skelcrew` label still starts it.

As a **source**, the tracker gives Skelcrew issues. Every open issue in the copy shows as a task in stage `issue`. Skelcrew stores a task of its own once one starts, from the issue's title and body at that moment. Later edits to the issue don't reach a started task: the lead passes on what matters as an update, as today.

As a **mirror**, Skelcrew shows the task's progress in the tracker through the tracker's own signals, never comments, as `docs/learnings.md` says. It claims the issue with 👀, assigns it to you, and puts the line that closes it in the PR. A merged PR closes the issue. Closing an issue by hand ends nothing, as today: a task already working carries on until its PR merges or closes, or you remove it, since an issue closed as a duplicate or by mistake must not kill a builder mid-work. A task still in stage `issue` whose issue closes leaves the list. A task with no issue mirrors nothing, and the lead files an issue for it only when you ask.

## Files

A repository describes how its agents work in files, as it describes its build in a `Dockerfile` or its dependencies in `package.json`. Skelcrew ships the same files inside itself as its defaults. A repository with none of them works exactly as one does today.

This reverses the spec's "no roles, phases or flows as files". The roles were files already, inside Skelcrew's code, and the loop was fixed in code. Moving both into files lets a repository adjust them without a release of Skelcrew. Flows stay fixed stages with settings rather than a language, so Skelcrew still trusts capable agents and adds an adversarial review, rather than scripting them.

```
skelcrew.yaml            the repository's setup
skelcrew.lock            exact plugin versions, written by Skelcrew
.agents/
  roles/
    lead.md
    builder.md
    reviewer.md
  flows/
    default.yaml
  skills/
    <name>/SKILL.md
```

`AGENTS.md` stays where it is. Every harness reads it from the clone on its own, and Skelcrew doesn't touch it.

### `skelcrew.yaml`

The repository's setup, shared with everyone who works on it. It never holds a secret.

```yaml
# Shared with everyone who works on this repository. Never put a secret here.
tracker: github            # or linear, or none. Without a line, the forge's tracker
setup: [bun install]
test: [bun run check]
flow: default              # the flow a task gets unless it names another
plugins: [github]          # the plugins this repository needs, pinned in skelcrew.lock
limits: { threads: 4 }     # at most this many builders at once in this repository
```

This reverses the spec, which says `limits` is only ever yours and a `skelcrew.yaml` can't set it. The reason: how many builders a repository can take at once depends on the repository, not your machine. Each one runs its tests, uses its CI minutes and opens a PR its reviewers must read, and a team knows that cost. So `limits.threads` is the most builder threads running at once in this repository. A start over the limit, from `sc start`, the lead or the `skelcrew` label, isn't refused: its task waits in a queue, first come first served, as reviews wait today. The list and `sc ls` say `queued`, and the queue survives a restart of the engine. A labelled issue is claimed as it joins the queue, so another machine doesn't start it meanwhile. Without the line there is no limit, as today. Your `repos:` override can change it for you, as for any setting.

`limits.reviews`, how many reviews run at once on your machine, stays yours alone, since it fits your machine's cores.

The harness and model of each role move out of `skelcrew.yaml` and into the role's file.

### `.agents/roles/`

One file per role, named after it. The frontmatter holds its settings, and the rest is its instructions, which today live in `src/agents/prompts/` and in the reviewer's code.

```markdown
---
harness: codex
model: gpt-6.1-sol
---
You are the reviewer of a Skelcrew task. Read the diff against the base branch
adversarially …
```

`lead`, `builder` and `reviewer` always exist, from the built-in defaults when the repository has no file for them. A flow can name another role, such as `security-reviewer`, whose file the repository then provides. A role with no `harness` or `model` gets yours, from your personal config, as today.

### `.agents/flows/`

A flow is a fixed set of stages with settings. v6 has no flow language: the stages are always build, review, CI and ready, in that order, and a flow only sets how each one behaves.

```yaml
# .agents/flows/default.yaml
build:
  role: builder
review:
  role: reviewer
  rounds: 3              # after this many rounds of changes, the task needs you
ci: required             # required: ready waits for green checks. ignored: it doesn't
start: label             # label: the skelcrew label starts a task. ask: only you or the lead start it
```

A repository can have several flows, such as `docs.yaml` with a lighter reviewer. A task gets the flow `skelcrew.yaml` names unless `sc start --flow docs` names another. A task keeps its flow from start to end.

Who confirms what is part of the flow only where it is the repository's choice, such as whether a label starts a task. The human's own confirmations aren't settings: you always merge, you always add repositories, and you always say yes before a lead starts work or briefs another lead. No flow can drop them, as **Trust** says.

### `.agents/skills/`

A skill is a folder with a `SKILL.md`, in the format Claude Code reads: a name and a description in the frontmatter, and the instructions below, with any files they use beside it. Skelcrew uses that format as it is, so a skill written for Claude Code works unchanged, and nothing new is learned.

Skelcrew puts a repository's skills where each harness looks for them. Skills always come from Skelcrew's clone of the repository, at the `.agents/` you approved, and are copied in as a session starts. They go only into a folder that belongs to one session, never into one that sessions share, so an agent that edits its copy changes only its own session.

- **Claude Code.** Skelcrew copies them into the `skills/` folder of the session's own config folder, in `~/.local/share/skelcrew/claude/`. Every Claude Code session has one, reviews included.
- **Codex.** Codex reads skills from `skills/` in its `CODEX_HOME`. A Codex lead or builder already has a `CODEX_HOME` of its own, which holds its conversation, so its skills go into the `skills/` folder there. Reviews share Skelcrew's `CODEX_HOME`, whose `skills/` stays read-only and empty of any repository's skills, as `docs/learnings.md` says: anything there would steer every later review, in every repository. So a Codex review gets the repository's skills the third way, below, with paths into the thread's clone, which it sees through its throwaway layer.
- **Any other harness.** For a harness that reads no skills at all, or none in a folder of one session's own, Skelcrew adds one line per skill to the role's instructions, with its name, description and the path of its `SKILL.md`, so the agent reads the file when it needs it. Skills a repository keeps in `.claude/skills/` already reach Claude Code from the clone, as today, and Skelcrew leaves them alone.

### `skelcrew.lock`

The exact version and commit of every plugin `skelcrew.yaml` names. `sc add` and `sc update` write it, you commit it, and `sc install` installs exactly what it says on every machine, as `package-lock.json` does.

```yaml
# Written by sc add and sc update. Commit it.
github:
  source: skelcrew/skelcrew-github
  version: 0.3.1
  commit: 4f9c2e1a7b…
```

### Yours, never in a repository

What belongs to you or your machine stays in `~/.config/skelcrew/`, as today:

- every login and token, and each plugin's settings and sign-ins;
- the session host: `session: tmux`, or a session plugin such as `session: herdr`;
- your limits, such as `limits.reviews`;
- your default harness and model for each role;
- per-repository overrides, under `repos:`;
- your personal plugins, which no repository names, such as a session or machine plugin, pinned in `~/.config/skelcrew/skelcrew.lock`.

```yaml
# ~/.config/skelcrew/config.yaml
harness: claude
model: opus
session: herdr
limits: { reviews: 2 }
plugins: [herdr]
roles:
  reviewer: { harness: codex }
repos:
  simon/site:
    roles:
      builder: { model: sonnet }
```

### Built-in defaults

Skelcrew ships today's behaviour as the same files, inside Skelcrew: a `skelcrew.yaml` with no setup or test, the three roles with today's instructions, and a `default` flow with three rounds, CI required and the label starting tasks. So the defaults are read the same way a repository's files are, and nothing about them is special in the code.

`sc init` writes them out into a checkout, filled in from what it detects:

- **setup and test** from the files it finds, such as `bun install` and `bun test` for a `bun.lock`, `npm ci` and `npm test` for a `package-lock.json`, or `make test` for a `Makefile` with a `test` target. What it can't tell, it leaves as a commented example;
- **the forge** from the checkout's remote, which puts the forge's plugin in `plugins:` and locks it;
- **your harness and model** for each role, as real lines, so the repository works the same for a teammate.

It leaves any file that already exists as it is, and ends by saying the files count once you commit and push them to the default branch, as `sc init` does today.

### Which wins

Each setting comes from the first of these that sets it:

1. **Your per-repository overrides**, under `repos:` in your `config.yaml`. They are you, saying what you want for this repository on your machine.
2. **The repository's files**, from Skelcrew's clone of its default branch.
3. **Your general settings** in `config.yaml`.
4. **The built-in defaults.**

So the repository decides how its agents work, your general settings fill in what it leaves out, and an override is how you differ from your team on purpose. Settings merge key by key. A role's instructions are one value: a repository's `builder.md` replaces the built-in instructions whole, rather than adding to them.

Some settings exist only in one place. Logins, tokens, the session host, `limits.reviews` and personal plugins are only ever yours, and a repository's files can't set them. Nothing a repository sets can widen what **Trust** says it can't.

## Commands

The command line follows npm: files describe what a repository needs, `sc install` makes the machine match, and `sc add`, `sc remove` and `sc update` change the files and the machine together.

| Command | What it does |
| --- | --- |
| `sc` | Shows the list of the repository you are in. Starts the engine in the background first if it isn't running, and runs `sc install` first on a machine that isn't set up. |
| `sc init` | Writes `skelcrew.yaml` and `.agents/` from the built-in defaults, filled in from what it detects, and adds the repository. |
| `sc install` | Makes the machine match the files. Checks for `tmux`, `bwrap` or `sandbox-exec`, `git`, and every harness a role uses. Logs in each harness that has no login yet. Installs each plugin at its locked version, after showing what a new or changed one runs and asking. Runs each plugin's setup that hasn't run here. This is today's first run, and it is safe to run again: with nothing to do, it says so. In a checkout, it covers that repository and your personal files. Outside one, every repository Skelcrew has. |
| `sc add <plugin>` | Adds a plugin to the repository: `plugins:` in `skelcrew.yaml` and its exact version in `skelcrew.lock`. Then installs it, after asking. |
| `sc add -g <plugin>` | Adds a personal plugin: your `config.yaml` and your own lock file. Then installs it, after asking. |
| `sc remove [-g] <plugin>` | Takes a plugin out of the files and removes it from the machine once nothing else uses it. Refuses for the tracker or forge of a repository Skelcrew has. |
| `sc update [-g] [<plugin>]` | Moves a plugin, or all of them, to its newest tag, rewrites the lock, and installs it after asking. |
| `sc setup <plugin>` | Runs an installed plugin's setup again, such as to sign in when its sign-in lapsed. |
| `sc plugins` | Lists the plugins the files ask for and the machine has, with their versions and jobs, and any that `sc install` would change. |
| `sc up` | Runs the engine in the foreground, with a readable log. Ctrl-C stops the engine. Agents keep running in their session host, and the next engine reconnects to them. |
| `sc up --bg` | Runs the engine as the background service, under systemd or launchd, and returns. |
| `sc --remote <host> install` | Sends your personal files to the server and runs `sc install` there. On a server with no Skelcrew, asks, then puts Skelcrew there first. |
| `sc --remote <host> up --bg` | Runs the engine on the server as its background service. |
| `sc --remote <host> [command]` | Runs any command on the server, as today. With no command, opens the server's list. |

The commands for tasks and threads keep their names, and take task names:

| Command | In v6 |
| --- | --- |
| `sc start <issue>` | Makes a task from the issue and starts its builder thread. On a task that stopped, starts its threads again. Past the round limit, lets it go on. `--flow <name>` names its flow. |
| `sc start <repo> "<title>" "<description>"` | Makes a task with no issue, such as `app-t3`, and starts its builder thread. |
| `sc stop <task>[/<role>]` | Ends the task's sessions, or one thread's, and keeps the clone, branch and PR. |
| `sc rm <task>` | Closes the task: ends its threads, closes its PR, deletes its branch and clone, and takes you off its issue if Skelcrew assigned you. The issue stays open, so `sc start` starts it over. |
| `sc tell <task>[/<role>] "<text>"` | Types a message into the task's active thread, or the one named, and keeps it as an update to the task. |
| `sc review <task>` | Reviews the task's last submitted commit again. |
| `sc attach <task>[/<role>]` | Attaches full screen to the task's active thread, or the one named, through its session host. `sc attach lead` attaches to the lead. |
| `sc ps` | The threads, as today, one row each, named `app-12/builder`, with its status and needs you, its short title, and its task's PR, CI and review columns. |
| `sc ls` | The tasks, grouped by stage, with each task's PR, CI and review, as the list shows them. `--all` adds merged and closed ones. Replaces `sc issue ls`. |
| `sc show <task>` | One task: its description and updates as its reviewer gets them, its issue, its PR with CI and the latest review, and the end of a failed check's log. Replaces `sc issue show` and `sc pr show`. |
| `sc issue create <repo> "<title>" "<body>"` | Creates an issue in the tracker, as today. It now shows as a task in stage `issue`. |
| `sc repo add`, `ls`, `rm`, `trust` | As today. `sc repo trust` also approves changed `.agents/` files, as **Trust** says. |

Builders keep `sc submit`, `sc tell lead` and `sc review` for their own task.

`sc serve`, `sc plugin …` and `sc remote add` go. `sc up` replaces `sc serve`. `sc add`, `sc remove`, `sc update`, `sc setup` and `sc plugins` replace `sc plugin …`. `sc --remote <host> install` replaces `sc remote add` and the copying of the laptop's setup before every `sc --remote`: you send your setup when you change it, as you would run `npm install` after changing `package.json`. A `sc --remote` whose personal lock differs from the server's says so, and names the `install` that fixes it.

## Trust

Two kinds of thing could reach your machine through the files: plugins, which run as you, and a repository's own files, which steer agents. Each has its rule.

**Plugins run as you, outside the sandbox**, as today. So `sc install`, `sc add` and `sc update` never install a plugin silently, unlike npm. For a plugin that is new to this machine, or whose version or commit changed, they show its name, source, version, the commands its manifest runs, and the jobs it does, and ask. A plugin already installed at its locked version asks nothing. Without a terminal, such as for the engine, nothing is installed: the repository needs you, and its row says to run `sc install`. Agents can't run any of these commands, as they can't run `sc plugin` today.

**A repository's files steer agents, but can't grant anything.** `skelcrew.yaml` and `.agents/` can say how agents work. They can't:

- **widen the sandbox.** No file mounts a folder, passes an environment variable, or reaches a socket. The harness module draws the boundary, as today;
- **skip the human's confirmations.** You merge. You add repositories, in your own terminal. You say yes before a lead starts work, files a public issue, or briefs another lead. A flow can add confirmations, never remove these;
- **install anything without asking.** A plugin in `plugins:` is installed only through the asking above;
- **set what is yours**, such as logins, the session host and `limits.reviews`.

**A repository's `.agents/` needs your OK, the first time and after each change.** Role instructions and flows decide what agents are told and how far they go, so a change to them is a change to what runs on your machine. Skelcrew remembers the `.agents/` you approved for each repository, in your `~/.config/skelcrew/`, never in the repository.

The first time comes when a repository comes in. Adding a repository whose default branch already has an `.agents/`, by `sc`, `sc repo add` or `sc init`, shows what is in it and asks, even when Skelcrew would trust the repository on its own because you can push to it. Being able to push is not the same as having read what a teammate, or someone who got a change past review, wrote there. A yes approves it. A no still adds the repository, and its tasks run on the built-in roles and flows until `sc repo trust <repo>` approves its own. `sc init` in a checkout that already has an `.agents/` leaves it as it is and asks the same way. Files `sc init` writes itself are the built-in defaults, so they are approved as it writes them. A repository already in Skelcrew when it first reads `.agents/` asks the same way, at the first `sc` there.

After that, when the default branch brings an `.agents/` different from the one you approved, new tasks keep starting on the version you approved, and the repository needs you. `sc repo trust <repo>` shows what changed and asks, and a yes makes the new version count. A task that already started keeps the version it started with. When you merge with `m` a PR that changes `.agents/`, the confirm says so, and your yes approves it too.

## Session hosts

### The session interface

Every agent's session goes through one set of plain functions, which issue #283 puts in place, so the flow never names tmux. They come in two parts, which a session host always provides together.

The **session** part runs agents and lets you reach them:

| Function | What it does |
| --- | --- |
| `start` | Starts a session running the command Skelcrew gives, in a folder, with labels. The command is the sandboxed harness, so the host never changes what the agent can reach. Returns the session's ID. |
| `keys` | Sends keys, such as Esc. |
| `interrupt` | Stops the agent's turn, as Esc does. |
| `read` | Returns what the session shows now, for a test or a failed start. |
| `state` | Tells the host the agent's state, so its own screen and apps can show it. |
| `attach` | Attaches your terminal full screen to the session. It returns when you detach. |
| `end` | Ends the session. |
| `list` | Lists the host's sessions with Skelcrew's labels, so a starting engine finds the agents still running. |

The **transport** part carries text into an agent, for the messages module below:

| Function | What it does |
| --- | --- |
| `deliver` | Types a message into the session once the agent is idle, never into a turn still running and never on top of a person's unsent draft. |
| `idle` | Says when an agent becomes idle, so a waiting message can go. |

The transport belongs to the session host because text can only reach an agent through the terminal it runs in. So there is no messaging plugin of its own: installing a session plugin switches sessions and transport together.

tmux is the built-in host and keeps every trap in `docs/learnings.md`. Its transport learns idle from Skelcrew's hooks, with the screen covering the gaps **Agent state** lists. It delivers as today: it waits for a quiet pane with no busy mark and a bare prompt, checks again for a draft right before pasting, pastes as one bracketed paste, and sends Enter on its own a moment later. Alt-Q detaches.

### The session plugin job

A session plugin brings another host, as issue #284 describes. It is a new plugin job, `session`, with one command per function, run as the `call` command is: one JSON question on stdin, one JSON answer on stdout. `attach` runs in your terminal, as `setup` does.

```yaml
name: herdr
version: 0.1.0
skelcrew: 0.6.0
about: Runs Skelcrew's agents in herdr-core, so herdr's apps show them
jobs: [session]
session: [bun, session.ts]
attach: [bun, attach.ts]
```

`skelcrew/skelcrew-herdr` is the first. It maps the functions onto herdr-core: `start` onto `hc run`, `deliver` onto `hc send --if idle`, which waits for a person's draft and types only when the agent is idle, `idle` onto `hc events`, `keys` onto `hc send`, `read` onto `hc read`, `interrupt` onto `hc interrupt`, and `list` onto herdr's labels. Rex can follow the same way. A session plugin is always personal, added with `sc add -g`, since how you watch your agents is yours, not the repository's.

### Agent state

Skelcrew keeps each agent's state on its thread: `working`, `idle`, `asking` or `error`. It hands the state to the host with `state`. herdr hears it as OSC 7501, its program status protocol, so its apps show which agents work and which wait, with no screen reading of their own.

The state comes from the harness's hooks wherever a hook fires. The hooks are the ones Skelcrew already gives builders, and v6 gives the lead the same ones:

| Happens | Claude Code | Codex |
| --- | --- | --- |
| A message goes in | `UserPromptSubmit`: `working` | `UserPromptSubmit`: `working` |
| A turn ends normally | `Stop`: `idle` | `Stop`: `idle` |
| A turn ends on an error | `StopFailure`: `error` | No hook |
| The agent asks a question | `PreToolUse` on `AskUserQuestion`: `asking`, and `PostToolUse` ends it | No question tool: the agent ends its turn with the question, so `Stop` marks it `idle`, and a turn with no `sc submit` needs you, as today |
| You press Esc | No hook | `Interrupt`: `idle`. Builders don't get this hook today, and v6 adds it |

Two gaps have no hook: Esc on Claude Code, and an error on Codex, such as an unknown model, which prints its error and sits at its prompt. For these, Skelcrew still reads the screen, as it does today: an agent that shows `working` while its harness's busy mark, "esc to interrupt", is gone from its screen for a moment becomes `idle`. Skelcrew reads it with the host's `read`, so this works on every host. Neither gap flags needs you. After Esc you are looking at the agent anyway. A Codex error stays unnoticed, as today, except that Skelcrew checks a Codex model against `codex debug models` before it starts a session, which catches the commonest case.

On tmux, the screen is also still read before typing: `deliver` waits until the busy mark is gone and a line holds only the harness's bare prompt, so a message never lands in a turn still running or on top of a person's unsent draft. No hook can say either. On herdr, `hc send --if idle` makes the same checks, and the transport learns idle from `hc events`, which carry the state Skelcrew reported and herdr's own view of the terminal.

So hooks decide every state they can see, the screen covers the two gaps and the typing, and every host shows the same state.

### Labels

Every session carries three labels: its repository (`simon/app`), its task (`app-12`) and its role (`builder`, or `lead` for a lead). `list` finds Skelcrew's sessions by them, and herdr's apps can group and filter by them.

### Changing host

Your `session:` setting picks the host for new sessions. Each thread remembers the host it started on, and an agent already running stays there until it ends. A resumed agent, such as after `sc stop` and `sc start`, starts on the current host with its conversation, since the conversation belongs to the harness, not the host. If a thread's host plugin is gone when the engine starts, the thread needs you, rather than being moved silently.

### Messages

Every message Skelcrew types into an agent goes through one module in core, on top of the transport. It holds the queue and the rules, and it is the same on every host:

- **Who may send what to whom.** The lead may tell any thread of its own repository. A builder may tell only its repository's lead. Skelcrew itself sends event messages to a builder: a review's changes, a failed check, a person's comment, a merge conflict. It sends notes to the lead: a thread that needs you, a task started from a label. A reviewer sends nothing. Anything else is refused.
- **The wrapping.** Every message from an agent is wrapped in a `<skelcrew from="…" reply="…">` tag, with `<skelcrew` and `</skelcrew>` removed from its text, so it never passes for yours.
- **Order.** Each agent has one queue, first in, first out, kept in the database, so a restart of the engine loses nothing and reorders nothing.
- **Waiting until idle.** A message waits until the transport says the agent is idle. A message to a thread that isn't running, or that is asking you a question, is refused, not kept, as today, since typing would answer the question for you. A note to a lead that hasn't started waits until it starts.
- **Dropping stale event messages.** When a new round starts, event messages about the old round that are still waiting, such as a failed check on an older commit, are dropped, since the builder has moved on and they would only mislead it. Messages from the lead and from you are never dropped.
- **Task updates.** A message from the lead, once typed in, is kept on the task as an update, which the reviewer gets after the description.

**Later.** herdr has messaging between agents of its own. It could carry builders' reports to the lead, with Skelcrew's rules still deciding who may talk to whom. That is future work, not part of v6.

## Remote machines

The engine runs on the same machine as its agents: the daemon, polling, clones, sandboxes and reviews. So `--remote` becomes only "run `sc` on that machine", over plain `ssh -t`, with Skelcrew's version kept in step with the laptop's as today:

- `sc --remote <host> install` sets the server up from the files, as `sc install` does on the laptop. It sends your personal files there first: `config.yaml`, your lock file and the agents' Claude Code token. Each plugin's setup runs there once, in your terminal, as today. On a server with no Skelcrew, it asks, then puts Skelcrew there first.
- `sc --remote <host> up --bg` runs the engine there as its background service.
- `sc --remote <host> <command>` runs any other command there.

Seeing and talking to the agents from elsewhere is the session host's job, not Skelcrew's:

- **With tmux**, `sc --remote <host>` opens the server's list over SSH, and Enter attaches through tmux there, as today.
- **With herdr**, herdr's own machines (`hc machine add`) bring the server's terminals to your laptop, desktop and phone. No `--remote` is involved. You see and talk to the same leads and builders there, and merging stays in Skelcrew's list.

What of today's remote code goes away: `sc remote add` and its setting up of a server, the copying of your setup before every `sc --remote`, with `src/machine/copy-setup.ts` and the comparison that decides what changed, and the special first run there, as `sc install` covers it. What stays: the `ssh -t` passthrough with `--from`, the shared SSH connection, the offer to set up a machine that isn't, the version check and the update with its Linux build or download, and machine plugins.

## The list

`sc` shows a list, modelled on herdr-core's own interface: a picker, not a layout. You pick a row, and Skelcrew either attaches you full screen to an agent or does what the row offers. Detaching brings you back to the list. There is no sidebar, no split, and no tmux server of the screen's own.

```
 Skelcrew v0.6.0 · app                                        site •1  docs

 ◆ lead            idle · claude
                   asks: start a task on #31 "Export as CSV"?          y/n

 Issues
   ○ app-31        Export as CSV
   ○ app-29        Dark mode for the settings page

 Working
   ● app-24        Login redirect          working · claude · round 2 · 12m
   ● app-t3        Rate limit the API      needs you: question · codex
   ○ app-27        Faster search           checks · #44

 Ready for review
 ▸ ● app-22        Fix the export header   #41 · approved · CI passed

 ↑↓ move  ⏎ open  m merge  y/n answer  ⇥ repository  q quit   cpu 63%  mem 9/32G
```

The list is the repository's, picked as plain `sc` picks one today: the checkout you are in, or the one you opened last. The top line names the other repositories, each with a yellow count when something there needs you, and Tab moves to the next one. Its parts are:

- **The lead**, first. Its row says what it is doing. Requests from the lead that wait for your yes, such as starting a task, adding a repository or briefing another lead (#275, #282), show under it, one per line, newest first.
- **Issues**: tasks in stage `issue`, not started.
- **Working**: tasks with agents on them. The row says what is happening, and when a thread needs you, why, in yellow. A task with more than one live thread shows each under it, as `app-24/builder`.
- **Ready for review**: Skelcrew's reviewer approved and CI is green. Each waits for you.

The marks and colours keep today's meaning: green is good, yellow wants you, red is wrong, and a dim `○` waits. The word always says what is happening, so nothing is told by colour alone.

| Key | On | What it does |
| --- | --- | --- |
| ↑ ↓ | Anywhere | Move one row |
| Enter | The lead | Attaches full screen to the lead |
| Enter | Issues | Asks `Start app-31? y/n` in the bottom line, then starts the task |
| Enter | Working | Attaches full screen to the task's active thread, through its session host. Detaching returns to the list, on the same row |
| Enter | Ready for review | Opens the PR in your browser, or copies its link when Skelcrew runs on a server |
| `m` | Ready for review | Asks `Merge app#41 into main? y/n`, then merges it on the forge |
| `y` `n` | A request from the lead | Answers it |
| Tab | Anywhere | The next repository |
| `q` | Anywhere | Leaves the list. Everything keeps running |

The list reads only Skelcrew's database, so it opens at once, and writes to the terminal only when what it shows changes, as today's lists do. The machine's load stays at the end of the bottom line. Merging and starting stay yours: the lead can't press these keys.

With herdr as the session host, its own apps show the same agents, labelled and with their state. Skelcrew's list keeps working beside them, and is the only place that merges and answers the lead's requests.

### What goes away

The split-screen app: the sidebar and its rows, the tabs, the header and the strip, the footer's keys, the lists of issues, PRs and threads, the issue and PR pages, the list of keys, the copying through two tmux servers, and the screen's own tmux server. `sc show` and the PR on its forge take the place of the pages. That is most of `src/screen/`, and most of the traps under **The screen** in `docs/learnings.md`.

## Migration

No rewrite. Each phase lands as small pull requests that pass `bun run check`, merges on its own, and leaves Skelcrew working for every thread already running. `docs/spec.md` is updated in the same pull request as the behaviour it describes.

### Phase 0: clear the decks

- **What changes.** The pipeline fixes already in flight are finished and merged. Work on the split-screen screen is parked: no new features there, only fixes for something broken.
- **Depends on.** Nothing.
- **Risky.** Nothing new.
- **Tested.** As those fixes already are.

### Phase 1: seams, with no change in behaviour

- **What changes.** Sessions go behind the interface above (#283), implemented by tmux alone, with its transport. The messages module takes over the queue and the rules from the code that types messages today, on that transport. Dropping stale event messages when a new round starts is its one new rule. The settings are read by one loader, which merges built-in defaults, the repository's `skelcrew.yaml` and your `config.yaml` in the order above. The roles' instructions move from `src/agents/prompts/` and the reviewer's code into built-in default files, in the same shape as `.agents/`, and are read from there.
- **Depends on.** Phase 0.
- **Risky.** The messages module touches every message an agent gets, so a mistake there loses or repeats one. The session interface and the transport have one implementation until phase 5. That goes against "no abstraction before the second use", and is accepted because the second use is planned, and because the seam lets phases 2 to 4 be written without tmux in mind. It is plain functions in one module, with no class or factory.
- **Tested.** Every existing test passes unchanged, which is the proof that nothing changed. New tests check the loader's order with fake files, that the built-in files give the same instructions the code gave, and each rule of the messages module against a fake transport: who may send to whom, order, waiting until idle, refusals, and dropping a stale event message when a new round starts.

### Phase 2: tasks

- **What changes.** A database migration adds a tasks table. Every existing thread becomes a task with one builder thread, keeping its name, folder, branch, session and PR. The task takes the title, body, short title, updates, PR, checks, rounds, review state and assignment. The thread keeps its role, harness, session, status and needs you. Commands take task names, and `task/role`. Open issues show as tasks in stage `issue`. `sc ls` and `sc show` arrive, and `sc issue ls`, `sc issue show` and `sc pr show` become short names for them until phase 6.
- **Depends on.** Phase 1.
- **Risky.** The database migration, on machines with threads running. It only adds: new tables and columns, filled from the old ones, which stay and are no longer read, as the `open_items` table did. So only one daemon may use the database across the migration. It runs when the new release's daemon starts, and one daemon per machine already means that happens only once the old one has stopped. Agents keep running in their sessions meanwhile, as through any update. After the migration, nothing of the old release writes to the database: its daemon has gone, and an old screen still open only reads. Running the old release again afterwards is not supported, since what it wrote would go into columns the new code ignores. The way back is the copy of `skelcrew.db` Skelcrew makes beside it before migrating. The migration runs once, inside one transaction.
- **Tested.** Database files saved from the current release, with threads in every status, are migrated in tests. Each command then shows the same threads under the same names. A test checks that the new daemon refuses to start, and so to migrate, while another daemon holds the socket. Another checks that a thread's rounds, PR, review and updates written just before the migration show up on its task after it.

### Phase 3: configuration as files

- **What changes.** `sc init` writes the files, with detection. Skelcrew reads `.agents/` and the new `skelcrew.yaml` from its clone of the default branch. Fixed-stage flows replace the hard-coded loop, with the `default` flow giving today's behaviour. Skills are linked in for each harness. Trust for `.agents/` arrives with `sc repo trust`. A repository with only today's `skelcrew.yaml` keeps working: its harness and model lines are read as the roles' until it has role files.
- **Depends on.** Phases 1 and 2.
- **Risky.** Trust. A mistake here lets a repository's files run something you didn't approve. So the checks are tested first, and an `.agents/` that isn't approved never runs.
- **Tested.** Repositories in temporary folders with and without each file, checking the order of settings, that a changed `.agents/` holds new tasks back until `sc repo trust`, that no file can set what is yours, and that `sc init` detects setup and test from sample checkouts. The flow's settings are tested through the pure code that decides what an event means, with no clock, files or network.

### Phase 4: the npm-style lifecycle

- **What changes.** `sc install`, `sc add`, `sc remove`, `sc update`, `sc setup` and `sc plugins`, with `skelcrew.lock` and your own lock. The first run becomes `sc install`. `sc up` and `sc up --bg` replace `sc serve` and the service install. `sc --remote <host> install` replaces `sc remote add` and the copying of your setup, and `sc --remote <host> up --bg` runs the engine there. `src/machine/copy-setup.ts` and the setup comparison in `--remote` go.
- **Depends on.** Phase 3, for `plugins:` in `skelcrew.yaml`.
- **Risky.** Trust again: every path that installs a plugin must ask. Moving machines that run today's setup: their installed plugins are written into your lock as they are, so nothing is reinstalled and nothing is asked again. A server set up by `sc remote add` must keep working: its setup is already there, so its first `sc --remote <host> install` changes nothing.
- **Tested.** Fake plugins in local git repositories with version tags, never GitHub. `sc install` run twice changes nothing the second time. A changed commit in the lock asks again. Without a terminal, nothing installs. `--remote` is tested against a fake `ssh`, as today, including `install` on a server set up the old way.

### Phase 5: session plugins

- **What changes.** The `session` plugin job (#284), carrying both sessions and the transport, then `skelcrew/skelcrew-herdr` in its own repository, delivering with `hc send --if idle` and learning state from `hc events`. Agent state is kept on the thread, from hooks and from the screen where no hook fires, and goes to the host with `state`. Codex builders get the `Interrupt` hook. Each thread remembers its host.
- **Depends on.** Phase 1 for the interface, phase 4 for `sc add -g`.
- **Risky.** Typing into a session. Every trap in `docs/learnings.md` about it was learned on tmux, and a new host must honour them, the draft check above all. Recovery: an engine that starts must find agents on two hosts at once.
- **Tested.** A fake session plugin, a short script that keeps sessions in a folder, runs the same tests tmux runs. A thread started on tmux keeps running there after the host changes. `skelcrew-herdr` is tested in its own repository.

### Phase 6: the list

- **What changes.** `sc` shows the list. Enter attaches through the session host. `m`, `y` and `n` work there. The split-screen app and its tmux server are removed, with their tests and their part of `docs/learnings.md`. The short names kept in phase 2 go.
- **Depends on.** Phase 2 for tasks and stages, phase 5 for attaching through any host.
- **Risky.** People used to the sidebar lose it. The list must reach a thread that needs you as quickly as the sidebar did: one row and Enter.
- **Tested.** The list is drawn on a tmux socket of the test's own, as the screen tests are today, with fake tasks in each stage. Attaching and detaching return to the same row. A merge and a start each ask first.

## Open questions

Each has the answer this document assumes until someone decides otherwise.

1. **How far do flows go after v6?** Assumed: fixed stages with settings, and no flow language. Extra stages, such as a security review or a deploy check, wait until a real repository needs one.
2. **Which format do skills use?** Assumed: Claude Code's `SKILL.md` folders, linked where each harness looks, and listed in the instructions for a harness that reads none. If a shared format for skills settles across harnesses, Skelcrew follows it.
3. **One PR per task?** Assumed: yes. A task across repositories, with a PR in each, would come with projects, as the spec's list of what isn't in this version describes.
4. **Does every open issue appear as a task?** Assumed: yes, in stage `issue`, as every open issue shows in today's list. A repository with hundreds of open issues may need a filter, such as only issues with a label, which would be a setting in `skelcrew.yaml`.
5. **Should reviewers become threads?** Assumed: not in v6. They stay fresh one-off runs, and **Reviewers** says how a flow could keep one.
6. **How does herdr group repositories?** herdr-core has no workspaces. Assumed: Skelcrew labels each session with its repository, task and role, and herdr's app groups by the repository label. If herdr adds workspaces, the plugin maps a repository onto one.
7. **How is the background engine stopped?** Assumed: with systemd or launchd's own commands, and no `sc` command of its own, since agents keep running either way.
8. **Can a flow pick its start by issue label?** Assumed: no. The `skelcrew` label starts the repository's default flow, and another flow is named with `sc start --flow`.
9. **Should herdr's messaging between agents carry builders' reports to the lead?** Assumed: not in v6. Every message goes through Skelcrew's module and the session host's transport.
