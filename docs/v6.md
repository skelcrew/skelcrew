# Skelcrew v6

Nov 17, 2026 · design, not yet built · `docs/spec.md` still describes what Skelcrew does today, and is updated phase by phase as this lands

## Why

Skelcrew today is half a multiplexer. It runs its own split-screen terminal app, with a second tmux server, a sidebar, tabs, lists, pages and a footer. That part has grown into the biggest and most fragile part of the code, and it competes with tools that do nothing else.

v6 makes Skelcrew thinner and easier to combine with other tools. It becomes closer to a workflow manager: Docker for running agents.

- The repository describes how its agents work, in files, as a `Dockerfile` or `package.json` does. Skelcrew is the engine that runs what the files say.
- Agents run in a session host. tmux is the default. A runtime plugin can bring another, such as herdr-core (`hc`, https://github.com/herdrdev/herdr-core), and later Rex. With herdr, its desktop and mobile apps show Skelcrew's leads and builders and let you chat with them. No host is the main one: tmux and Skelcrew's own list are the default, and plugins make the others possible. A plugin takes over only the base modules it provides, and Skelcrew's built-ins do the rest.
- Issues, threads and PRs stop being three objects. Skelcrew keeps tasks, and each task has threads.
- The command line works like npm's.
- The screen becomes a simple list, a picker rather than a layout.

## What stays

Most of Skelcrew stays as `docs/spec.md` describes it. Agents still work the same way: a lead, builders in sandboxes, an adversarial reviewer, and you merging. But v6 does change how some of that work runs, not only how it is shown, and **What changes** lists every such change.

- **The lead.** One per repository, on your harness, always running, seeing only its repository. It proposes, you say yes, it starts work.
- **The sandbox.** bubblewrap on Linux and `sandbox-exec` on a Mac, drawing the same boundary. A thread's own clone and branch. No tokens inside. Agents never call GitHub. Every trap in `docs/learnings.md` still applies.
- **The harness modules.** Claude Code and Codex, one module each, with their hooks (`Stop`, `StopFailure`, Codex's `Interrupt`) and their logins. Harnesses are still never plugins, since the module draws the sandbox boundary.
- **Tracker and forge plugins**, now called I/O plugins. The `call` questions and answers, the GitHub plugin, Skelcrew's GitHub App and its service. How a plugin is installed changes, and its manifest says it is I/O in place of a list of jobs.
- **The build ⇄ review loop.** A builder submits with `sc submit`. A fresh reviewer, on another model if you choose, reviews adversarially and answers in a fixed shape. Changes go back to the builder. The round limit, the review queue and `limits.reviews` stay.
- **CI and the PR's events.** Failed checks, people's comments, merge conflicts and merges wake the builder or end the work, as the events table in the spec says.
- **What ends work.** A task's work ends only when its PR merges or closes, or you remove it. Closing an issue by hand still ends nothing.
- **Needs you.** The same reasons, from the same hooks, told to the lead the same way.
- **The daemon.** One per machine. Agents keep running through its restart, and it reconnects to them, resumes their conversations, and reruns reviews cut short.
- **`--remote`.** Over plain `ssh -t`, with the version kept in step with the laptop. It gets thinner, as **Remote machines** says.
- **Messages, in core, on every host.** `sc tell` between the lead and a builder, in `<skelcrew>` tags, the lead's messages as changes to the task that the reviewer sees, notes to the lead, and every rule about who may reach whom. They move into a module of their own, and stay in core whatever host runs the agents, since Skelcrew's rules and safety must be the same everywhere.
- **The sandbox stays in core** on every host too. A host runs the sandboxed command exactly as given.

## What changes

| Today | v6 |
| --- | --- |
| Issues, threads and PRs, three objects | Tasks, each with threads, an optional issue and one PR |
| Skelcrew keeps no tasks of its own | Skelcrew keeps tasks. The tracker is a source and a mirror |
| A thread is the work on a task | A thread is one agent working on a task, in a role |
| Roles and prompts are in the code | Roles, flows and skills are files in `.agents/`, with built-in defaults |
| `skelcrew.yaml` holds setup, test, harnesses and models | `skelcrew.yaml` holds the repository's setup. Roles hold harnesses and models |
| `sc plugin install`, the first run, `sc serve`, copying the laptop's setup to a server | `sc install`, `sc add`, `sc remove`, `sc update`, `sc up`, `sc --remote <host> install` |
| Plugins installed at their newest tag | Plugins locked to an exact version in `skelcrew.lock` |
| Agents run on Skelcrew's tmux server | Five base modules (sessions, transport, messages, sandbox, status), each with a built-in default. A plugin can provide sessions, transport and status's display, in any mix |
| An agent's state shows only on Skelcrew's screen, read partly from hooks and partly from the screen | An agent's state is kept on its thread, from hooks where a hook fires and from the screen where none does, and reported to the session host |
| `limits` is only ever yours | `skelcrew.yaml` can set `limits.threads`, how many builders run at once in the repository |
| A repository you can push to runs its files without a question | A repository's `.agents/` runs only once you approved it, the first time and after each change |
| A split-screen terminal app | A list you pick from, which attaches full screen |
| `sc remote add`, and your setup copied to the server before every `sc --remote` | `sc --remote <host> install` and `sc --remote <host> up --bg`. Seeing agents from elsewhere is the session host's job |
| Plugins do any of four jobs: tracker, forge, chat, machine | A plugin is either I/O (work in, results out) or runtime (where and how agents run), and says what it provides within that |
| Messages typed in by code spread across the flow | A messages module in core, on the built-in transport or one a plugin provides |

## Words

| Word | Meaning |
| --- | --- |
| Lead | Unchanged: your agent session for one repository, on your harness, always running. You talk to it. It proposes tasks and starts them once you say yes. |
| Repository | Unchanged: a git repository Skelcrew works on, from a clone of its own. |
| Task | What you want done, kept by Skelcrew: its title, description, flow, stage, the lead's updates, and links to the issue it came from and the PR it produced. One task makes at most one PR. |
| Issue | An item in a tracker, such as a GitHub issue or a Linear ticket. An issue can become a task. A task needs no issue. |
| Stage | Where a task is: `issue`, `working`, `ready for review`, `merged` or `closed`. |
| Flow | The stages a task goes through and their settings, such as the round limit and the reviewer's role. A file in `.agents/flows/`. |
| Role | What an agent does on a task: its instructions, harness and model. `lead`, `builder` and `reviewer` come built in. A flow can name others. A file in `.agents/roles/`. |
| Thread | One agent working on a task, in one role, on one harness, in one session. A task usually has one thread, its builder. |
| Builder | The role that writes the change. Its thread lives from the task's start until its PR merges or closes. |
| Reviewer | The role that reviews each round, fresh each time. In v6 it runs once per round and has no thread. |
| Round | One submit and the review of it. |
| Event | Something that happened to a task: a review, a PR comment, a failed check, a merge. |
| Needs you | A flag on a thread, shown on its task: a question, a stop without submitting, a harness error, the round limit, a failed review. A task in `ready for review` waits on you too, by its stage. |
| Skill | Knowledge an agent loads when it needs it, as a folder with a `SKILL.md`. A folder in `.agents/skills/`. |
| Session host | What runs agents' sessions and lets you attach to them: tmux, or a plugin that provides sessions, such as herdr. |
| Base module | One of the five parts that run agents: sessions, transport, messages, sandbox and status. Each has a built-in default, and a plugin can provide some. |
| Plugin | A program in a repository of its own, of one of two kinds. An I/O plugin brings work in and sends results out, such as GitHub. A runtime plugin provides some of where and how agents run, such as herdr. |
| I/O plugin | A plugin for work in and results out: issues become tasks, labels start them, comments and reviews reach builders, and PRs, reviews, checks, merges, closed issues and notifications go out. It provides tracker, forge or chat. |
| Runtime plugin | A plugin for where and how agents run. It provides some of the base modules sessions, transport and status, or a machine. |
| Lock file | `skelcrew.lock`: the exact version and commit of every plugin a repository uses. |

Tracker items are called issues everywhere: in commands, in the list and in the lead's words. The word task means Skelcrew's own object only.

## Tasks and threads

### Tasks

A task is Skelcrew's own record of a piece of work, from the first words to the merge. It has:

- a **name**, such as `app-12` or `app-t3`;
- a **title** and a **description**, which the builder gets as its first message;
- a **flow**, named when it starts, `default` unless said otherwise;
- a **stage**: `issue`, `working`, `ready for review`, `merged` or `closed`;
- the **lead's updates**: every message the lead typed into one of its threads after it started, in order, with who sent it and when. The reviewer gets them after the description, as it does today, under "Changes to the task from the lead, after the thread started";
- a link to the **issue** it came from, if it came from one;
- a link to the **PR** it produced, once there is one, with its CI state and Skelcrew's review state: the round, the reviewer, the verdict.

The stages mean:

| Stage | When |
| --- | --- |
| `issue` | An open issue with no work running on it: never started, or started and then removed with `sc rm`. A task with no issue never has this stage: it starts in `working`. |
| `working` | Agents are on it: the builder works, a review runs, CI runs, or a thread needs you. A task whose thread stopped or failed stays here too, so it doesn't vanish. |
| `ready for review` | Skelcrew's reviewer approved the latest round and CI is green. It waits for the human: you review and merge. Without a forge, the branch is approved and waits for you. |
| `merged` | The PR merged, or without a forge, the branch's changes reached the default branch. |
| `closed` | The work ended without a merge, by `sc rm` or a PR closed without merging, and there is no open issue behind it. Or its issue closed while it was still in stage `issue`. |

`merged` is the end. `closed` is the end unless you start the task again with `sc start`, which moves it back to `working`. The list shows neither, and `sc ls --all` shows both.

When the work on a task ends without a merge and its issue is still open, the task goes back to stage `issue`, not to `closed`. That is today's behaviour told as a stage: after `sc rm app-12`, issue #12 shows as not started again. It is the same task, with the same name. Its threads, its closed PR and the lead's updates stay in its log, and `sc show app-12` lists them as an earlier attempt under the issue. `sc start app-12` starts the same task again, from the issue's title and body as they are then, in a fresh clone on a fresh branch, with no updates carried over, as `sc start` after `sc rm` does today. A task with no issue, such as `app-t3`, goes to `closed`, and `sc start app-t3` starts the same task again from its own title and description, moving it from `closed` back to `working`.

Needs you stays a flag on a thread, never a stage. A task in `working` can need you, and the list shows why in its row.

### Names

A task has one name, used everywhere. It is the issue's ID with the repository's short name in front when the ID doesn't name a repository, as today: GitHub issue #12 in app is `app-12`, and Linear's `JOTT-12` stays `JOTT-12`. A task with no issue gets a `t` and a number of Skelcrew's: `app-t3`. A task's name comes from its issue's ID and never changes, so you can always tell which issue a task is: `app-12` is #12 in app.

A thread is addressed as its task and its role: `app-12/builder`. Wherever a command takes a thread, the task's name alone means its active thread: the one that needs you, or else its builder. So `sc attach app-12` and `sc tell app-12 "…"` work as they do today. The slash never needs quoting in a shell.

### Threads

A thread is one agent on a task. It has:

- its **role**, such as `builder`, or one a flow defines;
- its **harness** and **model**, from the role, kept for the thread's life, since a conversation can't move between harnesses;
- its **session**: the session host it runs on and the session's ID there;
- its **state**: `working`, `idle`, `asking` or `error`, from Skelcrew's hooks, and its status as today: `working`, `waiting`, `failed`, `stopped` or `done`;
- its **needs you** reasons;
- for a builder, the task's **branch and clone**, which the builder owns.

Today's thread becomes a task with one builder thread. Everything that belongs to the work rather than the agent moves to the task: the title, description, short title, the lead's updates, the PR, CI, the round count and the review state, and whether Skelcrew assigned you the issue.

### One PR per task

A task makes at most one PR, from its builder's branch. Work that needs two PRs is two tasks, and the lead says which comes first with `sc tell`, as today. This keeps the stage of a task as plain as the state of one PR. Whether a task should ever hold several PRs, such as one per repository, is an open question at the end.

### Reviewers

Reviewers stay one-off runs in v6: a fresh agent for each round, with no session and no thread, as today. A review is recorded on the task, as part of its review state.

They could become threads later. A flow would say `review: { role: reviewer, keep: true }`, and the reviewer would be `app-12/reviewer`, with a session of its own. Each round's diff would be typed into that session, so the reviewer remembers what it asked for, and you could attach to it and ask why. The cost is the fresh view: a reviewer that remembers its last round can come to share the builder's blind spots. So it stays a choice for later, and the default stays fresh.

### The tracker is a source and a mirror

Today the spec says Skelcrew keeps no tasks of its own: you plan in the tracker, and Skelcrew follows it. v6 reverses this. Skelcrew keeps tasks, and the tracker is where many of them come from and where Skelcrew shows how they are going.

The reasons:

- Skelcrew already keeps tasks, in hiding. A thread with no issue keeps its title and body, and the lead's updates change every task after it starts, in Skelcrew only. So what the reviewer checks against was never just the issue.
- A task's life spans the issue, the agents and the PR. With three objects, every reader joins them again: the sidebar's three lists, `sc ps`, the strip. One object with a stage is simpler to show and to reason about.
- A flow, a stage and the lead's updates need a home that every tracker has, including no tracker at all.
- Trackers differ. Linear, Jira and GitHub each have their own states. Skelcrew's stages stay the same whichever one a repository uses.

What stays true: you still plan where you already do. An issue on GitHub still shows up in Skelcrew with nothing to write, and the `skelcrew` label still starts it.

As a **source**, the tracker gives Skelcrew issues. Every open issue in the copy shows as a task in stage `issue`. Skelcrew stores a task of its own once one starts, from the issue's title and body at that moment. Later edits to the issue don't reach a started task: the lead passes on what matters as an update, as today.

As a **mirror**, Skelcrew shows the task's progress in the tracker through the tracker's own signals, never comments, as `docs/learnings.md` says. It claims the issue with 👀, assigns it to you, and puts the line that closes it in the PR. A merged PR closes the issue. Closing an issue by hand ends nothing, as today: a task already working carries on until its PR merges or closes, or you remove it, since an issue closed as a duplicate or by mistake must not kill a builder mid-work. A task still in stage `issue` whose issue closes leaves the list. A task with no issue mirrors nothing, and the lead files an issue for it only when you ask.

## Files

A repository describes how its agents work in files, as it describes its build in a `Dockerfile` or its dependencies in `package.json`. Skelcrew ships the same files inside itself as its defaults. A repository with none of them works exactly as one does today.

This reverses the spec's "no roles, phases or flows as files". The roles were files already, inside Skelcrew's code, and the loop was fixed in code. Moving both into files lets a repository adjust them without a release of Skelcrew. Flows stay fixed stages with settings rather than a language, so Skelcrew still trusts capable agents and adds an adversarial review, rather than scripting them.

```
skelcrew.yaml            the repository's setup
skelcrew.lock            exact plugin versions, written by Skelcrew
.agents/
  roles/
    lead.md
    builder.md
    reviewer.md
  flows/
    default.yaml
  skills/
    <name>/SKILL.md
```

`AGENTS.md` stays where it is. Every harness reads it from the clone on its own, and Skelcrew doesn't touch it.

### `skelcrew.yaml`

The repository's setup, shared with everyone who works on it. It never holds a secret.

```yaml
# Shared with everyone who works on this repository. Never put a secret here.
tracker: github            # or linear, or none. Without a line, the forge's tracker
setup: [bun install]
test: [bun run check]
plugins: [skelcrew/skelcrew-github]   # the plugins this repository needs, pinned in skelcrew.lock
limits: { threads: 4 }     # at most this many builders at once in this repository
```

This reverses the spec, which says `limits` is only ever yours and a `skelcrew.yaml` can't set it. The reason: how many builders a repository can take at once depends on the repository, not your machine. Each one runs its tests, uses its CI minutes and opens a PR its reviewers must read, and a team knows that cost. So `limits.threads` is the most builder threads running at once in this repository. A start over the limit, from `sc start`, the lead or the `skelcrew` label, isn't refused: its task waits in a queue, first come first served, as reviews wait today. A queued task is in stage `working`, as it has left `issue` and is waiting for an agent, so the list shows it under Working with the word `queued`, as `sc ls` does. The queue survives a restart of the engine. `sc rm` takes a task out of the queue, and it goes back to `issue`, or to `closed` with no issue, as for any other `sc rm`. A labelled issue is claimed as it joins the queue, so another machine doesn't start it meanwhile. Without the line there is no limit, as today. Your `repos:` override can change it for you, as for any setting.

`limits.reviews`, how many reviews run at once on your machine, stays yours alone, since it fits your machine's cores.

The harness and model of each role move out of `skelcrew.yaml` and into the role's file.

### `.agents/roles/`

One file per role, named after it. The frontmatter holds its settings, and the rest is its instructions, which today live in `src/agents/prompts/` and in the reviewer's code.

```markdown
---
harness: codex
model: gpt-6.1-sol
---
You are the reviewer of a Skelcrew task. Read the diff against the base branch
adversarially …
```

`lead`, `builder` and `reviewer` always exist, from the built-in defaults when the repository has no file for them. A flow file names the roles it uses, so a repository that adds a flow file can add a role file for it. A role with no `harness` or `model` gets yours, from your personal config, as today.

### `.agents/flows/`

A flow is the stages a task goes through and their settings. There is no experience yet of what flows users need, so v6 doesn't guess. Skelcrew ships one flow, `default`, which is today's: build, review, CI and ready, in that order, with today's settings and no others. `sc init` writes it out:

```yaml
# .agents/flows/default.yaml: today's flow. Build, review, CI, ready.
build:
  role: builder
review:
  role: reviewer
  rounds: 3              # after this many rounds of changes, the task needs you
```

CI and ready have no settings, as today: ready waits for green checks when the repository has a forge. The round limit is the one setting today has, as `max_rounds`, and the roles name today's builder and reviewer, whose harness and model live in the role files.

**Picking a flow.** Every task gets `default`, unless the repository has added other flow files. Then the lead triages: it picks the flow when it starts or proposes a task, with `sc start --flow <name>`. Whenever it picks anything but `default`, it tells you, naming the flow and why. A task started from the `skelcrew` label gets `default`, unless the lead switches it, which it also tells you about. A task keeps its flow from start to end. The built-in lead's instructions say this, so it holds in every repository.

The human's own confirmations are never flow settings: you always merge, you always add repositories, and you always say yes before a lead starts work or briefs another lead. No flow can drop them, as **Trust** says.

Richer flows, such as custom stages, several reviewers, skipping stages, or picking a flow by label or rule, come later, once real use shows what is needed. They are in the open questions.

### `.agents/skills/`

A skill is a folder with a `SKILL.md`, in the format Claude Code reads: a name and a description in the frontmatter, and the instructions below, with any files they use beside it. Skelcrew uses that format as it is, so a skill written for Claude Code works unchanged, and nothing new is learned.

Skelcrew puts a repository's skills where each harness looks for them. Skills always come from Skelcrew's clone of the repository, at the `.agents/` you approved, and are copied in as a session starts. They go only into a folder that belongs to one session, never into one that sessions share, so an agent that edits its copy changes only its own session.

- **Claude Code.** Skelcrew copies them into the `skills/` folder of the session's own config folder, in `~/.local/share/skelcrew/claude/`. Every Claude Code session has one, reviews included.
- **Codex.** Codex reads skills from `skills/` in its `CODEX_HOME`. A Codex lead or builder already has a `CODEX_HOME` of its own, which holds its conversation, so its skills go into the `skills/` folder there. Reviews share Skelcrew's `CODEX_HOME`, whose `skills/` stays read-only and empty of any repository's skills, as `docs/learnings.md` says: anything there would steer every later review, in every repository. So a Codex review gets the repository's skills the third way, below, with paths into the thread's clone, which it sees through its throwaway layer.
- **Any other harness.** For a harness that reads no skills at all, or none in a folder of one session's own, Skelcrew adds one line per skill to the role's instructions, with its name, description and the path of its `SKILL.md`, so the agent reads the file when it needs it. Skills a repository keeps in `.claude/skills/` already reach Claude Code from the clone, as today, and Skelcrew leaves them alone.

### `skelcrew.lock`

The exact version and commit of every plugin `skelcrew.yaml` names. `sc add` and `sc update` write it, you commit it, and `sc install` installs exactly what it says on every machine, as `package-lock.json` does.

```yaml
# Written by sc add and sc update. Commit it.
skelcrew/skelcrew-github:
  name: github
  version: 0.3.1
  commit: 4f9c2e1a7b…
```

### Yours, never in a repository

What belongs to you or your machine stays in `~/.config/skelcrew/`, as today:

- every login and token, and each plugin's settings and sign-ins;
- the session host: `session: tmux`, or a runtime plugin such as `session: herdr`;
- your limits, such as `limits.reviews`;
- your default harness and model for each role;
- per-repository overrides, under `repos:`;
- your personal plugins, which no repository names, such as every runtime plugin, pinned in `~/.config/skelcrew/skelcrew.lock`.

```yaml
# ~/.config/skelcrew/config.yaml
harness: claude
model: opus
session: herdr
limits: { reviews: 2 }
plugins: [skelcrew/skelcrew-herdr]   # installed by its repository, then named by its short name, as in session: above
roles:
  reviewer: { harness: codex }
repos:
  simon/site:
    roles:
      builder: { model: sonnet }
```

### Built-in defaults

Skelcrew ships today's behaviour as the same files, inside Skelcrew: a `skelcrew.yaml` with no setup or test, the three roles with today's instructions, and the `default` flow, which is today's: build, review, CI and ready, with three rounds. So the defaults are read the same way a repository's files are, and nothing about them is special in the code.

`sc init` writes them out into a checkout, filled in from what it detects:

- **setup and test** from the files it finds, such as `bun install` and `bun test` for a `bun.lock`, `npm ci` and `npm test` for a `package-lock.json`, or `make test` for a `Makefile` with a `test` target. What it can't tell, it leaves as a commented example;
- **the forge** from the checkout's remote, which puts the forge's plugin in `plugins:` and locks it;
- **your harness and model** for each role, as real lines, so the repository works the same for a teammate.

It leaves any file that already exists as it is, and ends by saying the files count once you commit and push them to the default branch, as `sc init` does today.

### Which wins

Each setting comes from the first of these that sets it:

1. **Your per-repository overrides**, under `repos:` in your `config.yaml`. They are you, saying what you want for this repository on your machine.
2. **The repository's files**, from Skelcrew's clone of its default branch.
3. **Your general settings** in `config.yaml`.
4. **The built-in defaults.**

So the repository decides how its agents work, your general settings fill in what it leaves out, and an override is how you differ from your team on purpose. Settings merge key by key. A role's instructions are one value: a repository's `builder.md` replaces the built-in instructions whole, rather than adding to them.

Some settings exist only in one place. Logins, tokens, the session host, `limits.reviews` and personal plugins are only ever yours, and a repository's files can't set them. Nothing a repository sets can widen what **Trust** says it can't.

## Commands

The command line follows npm: files describe what a repository needs, `sc install` makes the machine match, and `sc add`, `sc remove` and `sc update` change the files and the machine together.

| Command | What it does |
| --- | --- |
| `sc` | Shows the list of the repository you are in. Starts the engine in the background first if it isn't running, and runs `sc install` first on a machine that isn't set up. |
| `sc init` | Writes `skelcrew.yaml` and `.agents/` from the built-in defaults, filled in from what it detects, and adds the repository. |
| `sc install` | Makes the machine match the files. Checks for `tmux`, `bwrap` or `sandbox-exec`, `git`, and every harness a role uses. Logs in each harness that has no login yet. Installs each plugin at its locked version, after showing what a new or changed one runs and asking. Runs each plugin's setup that hasn't run here. This is today's first run, and it is safe to run again: with nothing to do, it says so. In a checkout, it covers that repository and your personal files. Outside one, every repository Skelcrew has. |
| `sc add <plugin>` | Adds a plugin to the repository: `plugins:` in `skelcrew.yaml` and its exact version in `skelcrew.lock`. Then installs it, after asking. |
| `sc add -g <plugin>` | Adds a personal plugin: your `config.yaml` and your own lock file. Then installs it, after asking. |
| `sc remove [-g] <plugin>` | Takes a plugin out of the files and removes it from the machine once nothing else uses it. Refuses for the tracker or forge of a repository Skelcrew has. |
| `sc update [-g] [<plugin>]` | Moves a plugin, or all of them, to its newest tag, rewrites the lock, and installs it after asking. |
| `sc setup <plugin>` | Runs an installed plugin's setup again, such as to sign in when its sign-in lapsed. |
| `sc plugins` | Lists the plugins the files ask for and the machine has, with their versions, their kind and what each provides, and any that `sc install` would change. |
| `sc up` | Runs the engine in the foreground, with a readable log. Ctrl-C stops the engine. Agents keep running in their session host, and the next engine reconnects to them. |
| `sc up --bg` | Runs the engine as the background service, under systemd or launchd, and returns. |
| `sc --remote <host> install` | Sends your personal files to the server and runs `sc install` there. On a server with no Skelcrew, asks, then puts Skelcrew there first. |
| `sc --remote <host> up --bg` | Runs the engine on the server as its background service. |
| `sc --remote <host> [command]` | Runs any command on the server, as today. With no command, opens the server's list. |

The commands for tasks and threads keep their names, their options and what they do, and take task names. Every option of today's commands stays, and the table names the ones people use most:

| Command | In v6 |
| --- | --- |
| `sc start <issue> [--from <branch>] [--short "<words>"] [--flow <name>]` | Makes a task from the issue and starts its builder thread. On a task that stopped, starts its threads again. Past the round limit, lets it go on. Claims and assigns the issue, as today. `--from` and `--short` stay as today: the branch to start from, and the short title the list shows. `--flow` names its flow. |
| `sc start <repo> "<title>" "<description>" [--short "<words>"]` | Makes a task with no issue, such as `app-t3`, and starts its builder thread. Reads the title and description from stdin when they aren't given, as today. |

| `sc rm <task> ["<reason>"]` | Ends the work on the task: ends its threads, closes its PR with the reason as a comment when there is one, deletes its branch and clone, and takes you off its issue if Skelcrew assigned you. At a terminal it asks first, as today. The issue stays open, so `sc start` starts it over. |
| `sc tell <task>[/<role>] "<text>"` | Types a message into the task's active thread, or the one named, and keeps it as an update to the task. |
| `sc review <task>` | Reviews the task's last submitted commit again. |

Builders keep `sc submit`, `sc tell lead` and `sc review` for their own task.

`sc serve`, `sc plugin …` and `sc remote add` go. `sc up` replaces `sc serve`. `sc add`, `sc remove`, `sc update`, `sc setup` and `sc plugins` replace `sc plugin …`. `sc --remote <host> install` replaces `sc remote add` and the copying of the laptop's setup before every `sc --remote`: you send your setup when you change it, as you would run `npm install` after changing `package.json`. A `sc --remote` whose personal lock differs from the server's says so, and names the `install` that fixes it.

## Trust

Two kinds of thing could reach your machine through the files: plugins, which run as you, and a repository's own files, which steer agents. Each has its rule.

**Plugins run as you, outside the sandbox**, as today. So `sc install`, `sc add` and `sc update` never install a plugin silently, unlike npm. For a plugin that is new to this machine, or whose version or commit changed, they show its name, source, version, the commands its manifest runs, its kind and what it provides, and ask. A plugin already installed at its locked version asks nothing. Without a terminal, such as for the engine, nothing is installed: the repository needs you, and its row says to run `sc install`. Agents can't run any of these commands, as they can't run `sc plugin` today.

**A repository's files steer agents, but can't grant anything.** `skelcrew.yaml` and `.agents/` can say how agents work. They can't:

- **widen the sandbox.** No file mounts a folder, passes an environment variable, or reaches a socket. The harness module draws the boundary, as today;
- **skip the human's confirmations.** You merge. You add repositories, in your own terminal. You say yes before a lead starts work, files a public issue, or briefs another lead. A flow can add confirmations, never remove these;
- **install anything without asking.** A plugin in `plugins:` is installed only through the asking above;
- **set what is yours**, such as logins, the session host and `limits.reviews`.

**A repository's `.agents/` needs your OK, the first time and after each change.** Role instructions and flows decide what agents are told and how far they go, so a change to them is a change to what runs on your machine. Skelcrew remembers the `.agents/` you approved for each repository, in your `~/.config/skelcrew/`, never in the repository.

The first time comes when a repository comes in. Adding a repository whose default branch already has an `.agents/`, by `sc`, `sc repo add` or `sc init`, shows what is in it and asks, even when Skelcrew would trust the repository on its own because you can push to it. Being able to push is not the same as having read what a teammate, or someone who got a change past review, wrote there. A yes approves it. A no still adds the repository, and its tasks run on the built-in roles and flows until `sc repo trust <repo>` approves its own. `sc init` in a checkout that already has an `.agents/` leaves it as it is and asks the same way. Files `sc init` writes itself are the built-in defaults, so they are approved as it writes them. A repository already in Skelcrew when it first reads `.agents/` asks the same way, at the first `sc` there.

After that, when the default branch brings an `.agents/` different from the one you approved, new tasks keep starting on the version you approved, and the repository needs you. `sc repo trust <repo>` shows what changed and asks, and a yes makes the new version count. A task that already started keeps the version it started with. Merging a PR that changes `.agents/` approves nothing, since an agent wrote it, another reviewed it, and the merge confirm doesn't show the change. The confirm says the PR changes `.agents/`, and after the merge `sc repo trust` shows the change and asks, as for any other.

## Two kinds of plugin

A plugin is one of two kinds, and says in its manifest what it provides within that kind. This replaces today's flat list of jobs, tracker, forge, chat and machine, which #284 would have extended with session.

| Kind | What it is for | Provides | Examples |
| --- | --- | --- | --- |
| I/O | Work in and results out. In: issues become tasks, labels start them, comments and reviews reach builders. Out: PRs, reviews, checks, merges, closed issues and notifications | `tracker`, `forge`, `chat` | GitHub (tracker and forge), Linear, GitLab, Slack |
| Runtime | Where and how agents run | `sessions`, `transport`, `status`, `machine` | herdr and Rex. tmux is built in |

Messages and the sandbox stay in core, between the two. Work comes in through an I/O plugin, becomes a message, and reaches an agent through the runtime. What an agent produces goes back out the same way. Neither kind of plugin can provide messages or the sandbox, so the rules about who may reach whom, and what an agent can touch, are Skelcrew's on every setup.

```yaml
# skelcrew-github's manifest
name: github
version: 0.4.0
skelcrew: 0.6.0
about: Tasks from GitHub issues, and PRs on GitHub, as Skelcrew's GitHub App
kind: io
provides: [tracker, forge]
build: [[bun, install, --production]]
setup: [bun, setup.ts]
call: [bun, call.ts]
git_credentials: [bun, credentials.ts]
```

A plugin of today, with `jobs:` and no `kind:`, is still read: tracker, forge and chat make it I/O, and machine makes it runtime.

**The machine job** becomes part of the runtime side, since it is about where agents run. A runtime plugin can provide `machine`: how to reach a machine that runs Skelcrew, declared in its manifest as `add`, `exec` and `push` commands, as the spec describes them today:

```yaml
name: sprite
kind: runtime
provides: [machine]
add: [bun, add.ts]
exec: [bun, exec.ts]
push: [bun, push.ts]
```

Its built-in is SSH, as `--remote` uses today. So `sc --remote sprite:box install` reaches a Sprite through a runtime plugin that provides `machine`, and everything after that is `sc` running there, as **Remote machines** says. Like every runtime plugin, it is personal. Unlike the others, it is used on the laptop you run `--remote` from, never where the engine runs. No machine plugin exists yet: Sprites stay the planned first one.

## Base modules

How Skelcrew runs agents is split into five base modules. Each has a built-in default, which is today's behaviour. A plugin can take over some of them, and core uses its built-in for the rest. Nothing is all or nothing: a plugin that runs sessions doesn't have to carry messages too.

| Module | What it does | Built in | A plugin can provide it |
| --- | --- | --- | --- |
| Sessions | Runs each agent in a terminal session, lets you attach, and finds sessions again after a restart | tmux | Yes, such as herdr or Rex |
| Transport | Gets text into an agent, and knows when the agent is idle | Paste through the session, idle from Skelcrew's hooks and a screen check | Yes, such as herdr |
| Messages | Decides what is typed into which agent, when, and in what order | Core | No |
| Sandbox | Draws the boundary around every agent | Core: bubblewrap on Linux, `sandbox-exec` on a Mac | No |
| Status | Knows whether each agent works, idles, needs you, is ready or hit an error, and shows it | Core, from Skelcrew's hooks | Only the showing: a host that can display status gets it reported |

The flow speaks only to these modules, never to tmux or to a plugin by name. Phase 1 creates the modules with their built-ins, and phase 5 lets runtime plugins provide them with `provides:`.

### Sessions

| Function | What it does |
| --- | --- |
| `start` | Starts a session running the command Skelcrew gives, in a folder, with labels. Returns the session's ID. |
| `paste` | Pastes text into the session as one bracketed paste. |
| `keys` | Sends keys, such as Enter or Esc. |
| `read` | Returns what the session shows now. `sc peek` shows it to you. |
| `interrupt` | Stops the agent's turn, as Esc does. `sc interrupt` uses it. |
| `attach` | Attaches your terminal full screen to the session. It returns when you detach. |
| `end` | Ends the session. |
| `list` | Lists the host's sessions with Skelcrew's labels, so a starting engine finds the agents still running. |

The built-in is tmux, on Skelcrew's own tmux server, and keeps every trap in `docs/learnings.md`. Alt-Q detaches.

Every session carries three labels: its repository (`simon/app`), its task (`app-12`) and its role (`builder`, or `lead` for a lead). `list` finds Skelcrew's sessions by them, and a host's own apps can group and filter by them.

Your `session:` setting picks the host for new sessions. Each thread remembers the host it started on, and an agent already running stays there until it ends. A resumed agent, such as after `sc stop` and `sc start`, starts on the current host with its conversation, since the conversation belongs to the harness, not the host. If a thread's host plugin is gone when the engine starts, the thread needs you, rather than being moved silently.

### Transport

| Function | What it does |
| --- | --- |
| `deliver` | Types a message into an agent once it is idle, never into a turn still running and never on top of a person's unsent draft. |
| `idle` | Says when an agent becomes idle, so a waiting message can go. |

The built-in transport works on any host's sessions, as it uses only `paste`, `keys` and `read`. It learns idle from Skelcrew's hooks, with the screen covering the gaps **Status** lists. It delivers as today: it reads the screen until the busy mark is gone and a line holds only the harness's bare prompt, reads it again right before pasting in case a person started a draft, pastes, and sends Enter on its own a moment later. No hook can see a draft, so this screen check stays.

A host that can do better provides its own. herdr does: `hc send --if idle` waits for a person's draft and types only when the agent is idle, and `hc events` says when it is.

### Messages

Every message Skelcrew types into an agent goes through one module in core, on whichever transport is active. Its first version is #280, which lands in phase 0, and phase 1 moves it into this module unchanged. It holds the queue and the rules:

- **Who may send what to whom.** The lead may tell any thread of its own repository. A builder may tell only its repository's lead. Skelcrew itself sends event messages to a builder: a review's changes, a failed check, a person's comment, a merge conflict. It sends notes to the lead: a thread that needs you, a task started from a label. A reviewer sends nothing. A lead briefing another repository's lead arrives with #282: the lead asks, you say yes in the list, and only then is the brief delivered. Until then it is refused. Anything else is refused.
- **The wrapping.** Every message from an agent is wrapped in a `<skelcrew from="…" reply="…">` tag, with `<skelcrew` and `</skelcrew>` removed from its text, so it never passes for yours.
- **Order.** Each agent has one queue, first in, first out, kept in the database, so a restart of the engine loses nothing and reorders nothing.
- **Waiting until idle.** A message waits until the transport says the agent is idle. A message to a thread that isn't running, or that is asking you a question, is refused, not kept, as today, since typing would answer the question for you. A note to a lead that hasn't started waits until it starts.
- **Never dropped silently.** A message that hasn't been typed in after 10 minutes, such as to a builder that may have hung, brings a note to the lead, which can tell you. A message that is dropped, as the next rule says, goes in the thread's log. Nothing waits forever unseen.
- **Dropping stale event messages.** Event messages about an older round still waiting to be typed, such as a review's changes or a failed check on an older commit, are dropped once a newer round starts, since the builder has moved on and they would only mislead it. Events from the forge are checked again just before they are typed. Messages from the lead and from you are never dropped.
- **Task updates.** A message from the lead, once typed in, is kept on the task as an update, which the reviewer gets after the description.

Messages stay in core on every host, and no plugin can provide them. They are Skelcrew's rules and its safety: who may reach your lead, what passes for you, what the reviewer checks against. These must be the same whichever host runs the agents, or a host plugin could quietly let a builder steer another builder, or change what a task is reviewed against. A transport only carries text the module already decided to send.

### Sandbox

The sandbox stays in core on every host, drawn by the harness module, as today. A host runs the sandboxed command exactly as Skelcrew gives it, and never changes what the agent can reach. No plugin can provide it, and no repository file can widen it.

### Status

Skelcrew keeps each agent's state on its thread: `working`, `idle`, `asking` or `error`. With the thread's needs you and its task's stage, that gives the status a host shows: working, idle, needs you, ready or error.

The state comes from the harness's hooks wherever a hook fires. The hooks are the ones Skelcrew already gives builders, and v6 gives the lead the same ones:

| Happens | Claude Code | Codex |
| --- | --- | --- |
| A message goes in | `UserPromptSubmit`: `working` | `UserPromptSubmit`: `working` |
| A turn ends normally | `Stop`: `idle` | `Stop`: `idle` |
| A turn ends on an error | `StopFailure`: `error` | No hook |
| The agent asks a question | `PreToolUse` on `AskUserQuestion`: `asking`, and `PostToolUse` ends it | No question tool: the agent ends its turn with the question, so `Stop` marks it `idle`, and a turn with no `sc submit` needs you, as today |
| You press Esc | No hook | `Interrupt`: `idle`. Builders don't get this hook today, and v6 adds it |

Two gaps have no hook: Esc on Claude Code, and an error on Codex, such as an unknown model, which prints its error and sits at its prompt. For these, Skelcrew still reads the screen, as it does today: an agent that shows `working` while its harness's busy mark, "esc to interrupt", is gone from its screen for a moment becomes `idle`. Skelcrew reads it with the sessions' `read`, so this works on every host. Neither gap flags needs you. After Esc you are looking at the agent anyway. A Codex error stays unnoticed, as today, except that Skelcrew checks a Codex model against `codex debug models` before it starts a session, which catches the commonest case.

Skelcrew reports the status to the host when the host can show it. A plugin that provides status implements one function:

| Function | What it does |
| --- | --- |
| `status` | Receives a session's ID, its status word (`working`, `idle`, `needs you`, `ready` or `error`) and a short reason, such as `question` or `round limit`, each time the status changes, and shows it on the host. |

The engine calls `status` for every change, from wherever it came: a hook, the screen check, an event such as CI going green, or a review. herdr hears status as OSC 7501, its program status protocol, and that is an escape code written by the program running in the pane. The engine runs outside the pane, so it can't write one. So `skelcrew-herdr` writes it: its `start` runs the sandboxed command under a small relay of its own, the program herdr sees in the pane, which passes the agent's terminal through untouched and writes OSC 7501 into it when the plugin's `status` hands it a new status. The relay runs outside the sandbox, as the plugin does, and the sandboxed command inside it is exactly the one Skelcrew gave. Whether herdr-core can take a status over its API instead, which would need no relay, is an open question.

Rex shows a program activity status, and gets Skelcrew's through `status` if it accepts reports. tmux shows none, and Skelcrew's list shows it instead. A host's own view never replaces the hooks: needs you always comes from Skelcrew.

### Runtime plugins

A runtime plugin says in its manifest what it provides, out of four: the base modules `sessions`, `transport` and `status`, and `machine`. For the base modules, core uses its built-in for any it leaves out. Each of their functions is a command, run as the `call` command is: one JSON question on stdin, one JSON answer on stdout. `attach` runs in your terminal, as `setup` does.

```yaml
name: herdr
version: 0.1.0
skelcrew: 0.6.0
about: Runs Skelcrew's agents in herdr-core, so herdr's apps show them
kind: runtime
provides: [sessions, transport, status]
session: [bun, session.ts]       # start, paste, keys, read, interrupt, end, list, deliver, idle, status
attach: [bun, attach.ts]
```

- **herdr** (`skelcrew/skelcrew-herdr`, the first) provides sessions, transport and status. `start` maps onto `hc run`, `paste` and `keys` onto `hc send`, `read` onto `hc read`, `interrupt` onto `hc interrupt`, `attach` onto attaching your terminal through herdr-core's client, `end` onto ending the program, `list` onto herdr's labels, `deliver` onto `hc send --if idle`, `idle` onto `hc events`, and `status` onto OSC 7501, written by the plugin's relay in the pane.
- **Rex** is a terminal multiplexer with persistent sessions, remote and mobile clients, shared sessions and a program activity status, as far as its public pages at superlogical.com say. It shows no sign yet of an API or of messaging between agents. So a Rex plugin is assumed to provide sessions, and status if Rex accepts reports. Its agents then get messages through the built-in transport, pasting on Rex's sessions.

A runtime plugin is always personal, added with `sc add -g`, since how you watch your agents is yours, not the repository's. There is no messaging plugin: text can only reach an agent through the terminal it runs in, so carrying text belongs to the transport, and the rules stay in core.

**Later.** A host could carry messages between agents itself. herdr has messaging of its own, which could carry builders' reports to the lead. A plugin could provide that one day, with Skelcrew's messages module still deciding who may talk to whom. It is optional future work, and nothing in this design depends on it.

## I/O plugins

I/O plugins sit on the other side from the base modules. The base modules are where and how agents run: sessions, transport, messages, sandbox and status, on tmux, herdr or Rex. I/O plugins are where work comes from and where it goes: GitHub today, and Linear, GitLab or a chat such as Slack later. They keep the calls the spec describes, and say `kind: io` with what they provide, `tracker`, `forge` or `chat`, in place of their jobs. What changes is what Skelcrew does with their answers. The GitHub plugin is the example here.

- **The tracker is a source.** Tasks are Skelcrew's own. Every open issue shows as a task under Issues in the list. The `skelcrew` label still starts one, as today.
- **The tracker is a mirror.** When a task starts, Skelcrew claims the issue with 👀 and assigns it to you. When its PR merges, the issue closes. Both work as today. Showing a task's stage on the issue as a label is an open question.
- **The PR belongs to the task.** Opening it, posting reviews, the `skelcrew/check` status, CI results and merging all work as today. Their data is stored on the task: its PR, checks and review state. That is what the list shows under Ready for review.
- **CI failures say what failed.** The forge's `log` answer should give the failing tests and their errors, from the check run's annotations and the failed step, rather than the end of the job's log, where the cause is often far above the last lines. The change lives in the GitHub plugin alone. Skelcrew still types into the builder whatever `log` returns, so it can land at any time, in any phase.
- **Installing.** A repository declares the plugin in `skelcrew.yaml`, as `plugins: [skelcrew/skelcrew-github]`. `skelcrew.lock` pins its version, and `sc install` installs it, after asking. Then it runs the plugin's setup, the GitHub sign-in, when it is missing on this machine. The sign-in stays per machine, as today, since GitHub's renewing sign-in breaks when two machines share it.
- **Without a tracker or forge.** Tasks work from git alone, as a repository without a forge does today. Each task is started from what you told the lead, such as `app-t3`. Its branch is pushed with your git login, and the review loop runs the same.

## Remote machines

The engine runs on the same machine as its agents: the daemon, polling, clones, sandboxes and reviews. So `--remote` becomes only "run `sc` on that machine", over plain `ssh -t`, with Skelcrew's version kept in step with the laptop's as today:

- `sc --remote <host> install` sets the server up from the files. Your personal setup is one setup for all your machines, so a server feels like your laptop, as today. Your `config.yaml` and lock go there whole, `session:` included: `session: herdr` on the laptop means herdr on the server too, and the server installs herdr. The one exception is a runtime plugin that provides only `machine`: it is used where you run `--remote`, so the server skips it. Otherwise it works as `sc install` does on the laptop. It sends your personal files there first: `config.yaml`, your lock file and the agents' Claude Code token. Each plugin's setup runs there once, in your terminal, as today. On a server with no Skelcrew, it asks, then puts Skelcrew there first.
- `sc --remote <host> up --bg` runs the engine there as its background service.
- `sc --remote <host> <command>` runs any other command there.

Seeing and talking to the agents from elsewhere is the session host's job, not Skelcrew's:

- **With tmux**, `sc --remote <host>` opens the server's list over SSH, and Enter attaches through tmux there, as today.
- **With herdr**, herdr's own machines (`hc machine add`) bring the server's terminals to your laptop, desktop and phone. No `--remote` is involved. You see and talk to the same leads and builders there, and merging stays in Skelcrew's list.

What of today's remote code goes away: `sc remote add` and its setting up of a server, the copying of your setup before every `sc --remote`, with `src/machine/copy-setup.ts` and the comparison that decides what changed, and the special first run there, as `sc install` covers it. What stays: the `ssh -t` passthrough with `--from`, the shared SSH connection, the offer to set up a machine that isn't, the version check and the update with its Linux build or download, and machine plugins.

## The list

`sc` shows a list, modelled on herdr-core's own interface: a picker, not a layout. You pick a row, and Skelcrew either attaches you full screen to an agent or does what the row offers. Detaching brings you back to the list. There is no sidebar, no split, and no tmux server of the screen's own.

```
 Skelcrew v0.6.0 · app                                        site •1  docs

 ◆ lead            idle · claude
                   asks: start a task on #31 "Export as CSV"?          y/n

 Issues
   ○ app-31        Export as CSV
   ○ app-29        Dark mode for the settings page

 Working
   ● app-24        Login redirect          working · claude · round 2 · 12m
   ● app-t3        Rate limit the API      needs you: question · codex
   ○ app-27        Faster search           checks · #44

 Ready for review
 ▸ ● app-22        Fix the export header   #41 · approved · CI passed

 ↑↓ move  ⏎ open  m merge  y/n answer  ⇥ repository  q quit   cpu 63%  mem 9/32G
```

The list is the repository's, picked as plain `sc` picks one today: the checkout you are in, or the one you opened last. The top line names the other repositories, each with a yellow count when something there needs you, and Tab moves to the next one. Its parts are:

- **The lead**, first. Its row says what it is doing. Requests from the lead that wait for your yes, such as starting a task, adding a repository or briefing another lead (#275, #282), show under it, one per line, newest first.
- **Issues**: tasks in stage `issue`, not started.
- **Working**: tasks with agents on them. The row says what is happening, and when a thread needs you, why, in yellow. A task with more than one live thread shows each under it, as `app-24/builder`.
- **Ready for review**: Skelcrew's reviewer approved and CI is green. Each waits for you.

The marks and colours keep today's meaning: green is good, yellow wants you, red is wrong, and a dim `○` waits. The word always says what is happening, so nothing is told by colour alone.

| Key | On | What it does |
| --- | --- | --- |
| ↑ ↓ | Anywhere | Move one row |
| Enter | The lead | Attaches full screen to the lead |
| Enter | Issues | Asks `Start app-31? y/n` in the bottom line, then starts the task |
| Enter | Working | Attaches full screen to the task's active thread, through its session host. Detaching returns to the list, on the same row |
| Enter | Ready for review | Opens the PR in your browser, or copies its link when Skelcrew runs on a server |
| `m` | Ready for review | Asks `Merge app#41 into main? y/n`, then merges it on the forge |
| `y` `n` | A request from the lead | Answers it |
| Tab | Anywhere | The next repository |
| `q` | Anywhere | Leaves the list. Everything keeps running |

The list reads only Skelcrew's database, so it opens at once, and writes to the terminal only when what it shows changes, as today's lists do. The machine's load stays at the end of the bottom line. Merging and starting stay yours: the lead can't press these keys.

With herdr as the session host, its own apps show the same agents, labelled and with their state. Skelcrew's list keeps working beside them, and is the only place that merges and answers the lead's requests.

### What goes away

The split-screen app: the sidebar and its rows, the tabs, the header and the strip, the footer's keys, the lists of issues, PRs and threads, the issue and PR pages, the list of keys, the copying through two tmux servers, and the screen's own tmux server. `sc show` and the PR on its forge take the place of the pages. That is most of `src/screen/`, and most of the traps under **The screen** in `docs/learnings.md`.

## Migration

No rewrite. Each phase lands as small pull requests that pass `bun run check`, merges on its own, and leaves Skelcrew working for every thread already running. `docs/spec.md` is updated in the same pull request as the behaviour it describes.

### Phase 0: clear the decks

- **What changes.** Before phase 1 starts, the open pipeline PRs are finished and merged, as v6 builds on each of them:
  - **#280**, messages: they wait in the database, in order, are never dropped silently, drop stale event messages when a new round starts, and bring a note to the lead after 10 minutes. It becomes the first version of the messages module.
  - **#262**, harness usage limits and review timeouts. This is engine behaviour, which v6 keeps.
  - **#278**, the full suite once per commit. This is flow behaviour, which the default flow keeps.
  - **#261**, `sc peek` and `sc interrupt`. Phase 1 moves them onto the sessions module's `read` and `interrupt`.

  Work on the split-screen screen stays parked, since phase 6 removes it: #265, #266, #268, #274, #276 and the work on the sidebar's order. Only a fix for something broken lands there.

  The earlier issues for a session interface (#283) and a session plugin job (#284) are replaced by phase 1's base modules and phase 5's runtime plugins. They are rewritten as issues from this document.
- **Depends on.** Nothing.
- **Risky.** Nothing new: each PR is reviewed and merged on its own, as today.
- **Tested.** By each PR's own tests.

### Phase 1: the base modules

- **What changes.** The five base modules are created, each with its built-in: sessions on tmux, with `sc peek` and `sc interrupt` from #261 moved onto `read` and `interrupt`, the built-in transport on top of them, the messages module, which takes over #280's queue and rules unchanged, the sandbox as it is, and the built-in status, which does exactly what today's code does with the hooks it has today. Nothing changes in behaviour: the messages module keeps #280's rules exactly, and the status module keeps today's hooks and screen reads. The settings are read by one loader, which merges built-in defaults, the repository's `skelcrew.yaml` and your `config.yaml` in the order above. The roles' instructions move from `src/agents/prompts/` and the reviewer's code into built-in default files, in the same shape as `.agents/`, and are read from there.
- **Depends on.** Phase 0.
- **Risky.** The messages module touches every message an agent gets, so a mistake there loses or repeats one. Sessions and transport have one implementation each until phase 5. That goes against "no abstraction before the second use", and is accepted because the second use is planned, and because the seam lets phases 2 to 4 be written without tmux in mind. Each module is plain functions in a file of its own, with no class or factory.
- **Tested.** Every existing test passes unchanged, which is the proof that nothing changed. New tests check the loader's order with fake files, that the built-in files give the same instructions the code gave, each rule of the messages module against a fake transport (who may send to whom, order, waiting until idle, refusals, the note to the lead after 10 minutes, dropping a stale event message), carried over from #280's tests.

### Phase 1b: status from hooks

- **What changes.** The built-in status grows to what **Status** describes. Agent state is kept on the thread, from hooks and from the screen where no hook fires. The lead gets the same hooks as builders. Codex builders get the `Interrupt` hook, so a Codex builder stopped with Esc shows `idle` rather than `working`. This is a deliberate change in behaviour, kept apart from phase 1 so that phase 1 stays a pure seam.
- **Depends on.** Phase 1, for the status module.
- **Risky.** A wrong state could hold a message back or type into a busy agent. So the transport's screen check before typing stays, whatever the state says.
- **Tested.** Each row of the status table, with a fake harness that runs the hooks, plus the two screen gaps: Esc on Claude Code and an error on Codex. A test checks that the lead's hooks change its state and flag nothing.

### Phase 2: tasks

- **What changes.** A database migration adds a tasks table. Every existing thread becomes a task with one builder thread, keeping its name, folder, branch, session and PR. The task takes the title, body, short title, updates, PR, checks, rounds, review state and assignment. The thread keeps its role, harness, session, status and needs you. Commands take task names, and `task/role`. Open issues show as tasks in stage `issue`. `sc ls` and `sc show` arrive, and `sc issue ls`, `sc issue show` and `sc pr show` become short names for them until phase 6. The tracker works as a source and a mirror, as **I/O plugins** says: open issues show as tasks, the label starts one, and claiming, assigning and closing on merge work as today, with the task's data stored on the task.
- **Depends on.** Phase 1.
- **Risky.** The database migration, on machines with threads running. It only adds: new tables and columns, filled from the old ones, which stay and are no longer read, as the `open_items` table did. So only one daemon may use the database across the migration. It runs when the new release's daemon starts, and one daemon per machine already means that happens only once the old one has stopped. Agents keep running in their sessions meanwhile, as through any update. After the migration, nothing of the old release writes to the database: its daemon has gone, and an old screen still open only reads. Running the old release again afterwards is not supported, since what it wrote would go into columns the new code ignores. The way back is the copy of `skelcrew.db` Skelcrew makes beside it before migrating. The migration runs once, inside one transaction.
- **Tested.** Database files saved from the current release, with threads in every status, are migrated in tests. Each command then shows the same threads under the same names. A test checks that the new daemon refuses to start, and so to migrate, while another daemon holds the socket. Another checks that a thread's rounds, PR, review and updates written just before the migration show up on its task after it. A fake tracker and forge check that an open issue shows as a task in stage `issue`, that a label starts it, and that claiming, assigning and closing on merge happen as today.

### Phase 3: configuration as files

- **What changes.** `sc init` writes the files, with detection. Skelcrew reads `.agents/` and the new `skelcrew.yaml` from its clone of the default branch. The built-in `default` flow, read from its file, replaces the hard-coded loop and gives today's behaviour. The lead's instructions gain flow triage: in a repository with other flow files, it picks the flow with `sc start --flow` and tells you whenever it isn't `default`. Skills are copied in for each session, into a folder of that session's own. Trust for `.agents/` arrives with `sc repo trust`. Per-repository overrides under `repos:` in your `config.yaml` arrive, at the top of the order **Which wins** gives, and the loader from phase 1 gains that layer. `limits.threads` arrives: a repository's `skelcrew.yaml` can limit how many builders run at once, and a start over the limit waits in a queue of tasks, shown as `queued` under Working. Today's settings keep working, in their old shape, alongside the new one. In a repository's `skelcrew.yaml`, `lead:`, `builder:` and `reviewer:` are read as the roles' harness and model until it has role files, and `max_rounds` is read as the default flow's `rounds` until it has a flow file. In your `config.yaml`, `lead:`, `builder:` and `reviewer:` are read as `roles:`, and `max_rounds` as your default for `rounds`. Where both shapes say something, the new one wins. `sc` says once which old key it read and what replaces it, and changes no file itself.
- **Depends on.** Phases 1 and 2.
- **Risky.** Trust. A mistake here lets a repository's files run something you didn't approve. So the checks are tested first, and an `.agents/` that isn't approved never runs. The queue of tasks under `limits.threads` is new state: a task must never be lost from it or started twice, across a restart of the engine, a claim by another machine, or `sc rm`. And `repos:` must override only the repository it names.
- **Tested.** The queue: a start over `limits.threads` waits and shows `queued`, starts in order when a builder ends, keeps its place after a restart of the engine, and leaves the queue on `sc rm`, back to `issue`. A labelled issue in the queue is claimed once. `repos:` overrides beat the repository's files for that repository only. Repositories in temporary folders with and without each file, and with today's settings in their old shape, such as `max_rounds: 5`, which must still give five rounds, checking the order of settings, that a changed `.agents/` holds new tasks back until `sc repo trust`, that no file can set what is yours, and that `sc init` detects setup and test from sample checkouts. The flow's settings are tested through the pure code that decides what an event means, with no clock, files or network. A test checks that a task from a label gets `default`, and that `--flow` names another flow file of the repository.

### Phase 4: the npm-style lifecycle

- **What changes.** `sc install`, `sc add`, `sc remove`, `sc update`, `sc setup` and `sc plugins`, with `skelcrew.lock` and your own lock. The first run becomes `sc install`. `sc up` and `sc up --bg` replace `sc serve` and the service install. `sc --remote <host> install` replaces `sc remote add` and the copying of your setup, and `sc --remote <host> up --bg` runs the engine there. `src/machine/copy-setup.ts` and the setup comparison in `--remote` go. The manifest's `kind:` and `provides:` replace `jobs:`, which is still read, and the GitHub plugin's manifest says `kind: io`. The GitHub plugin is declared in `skelcrew.yaml`, pinned in `skelcrew.lock` and installed by `sc install`, as **I/O plugins** says.
- **Depends on.** Phase 3, for `plugins:` in `skelcrew.yaml`.
- **Risky.** Trust again: every path that installs a plugin must ask. Moving machines that run today's setup: their installed plugins are written into your lock as they are, so nothing is reinstalled and nothing is asked again. A server set up by `sc remote add` must keep working: its setup is already there, so its first `sc --remote <host> install` changes nothing.
- **Tested.** Fake plugins in local git repositories with version tags, never GitHub. `sc install` run twice changes nothing the second time. A changed commit in the lock asks again. Without a terminal, nothing installs. `--remote` is tested against a fake `ssh`, as today, including `install` on a server set up the old way.

### Phase 5: runtime plugins

- **What changes.** Runtime plugins, with `provides:` naming the base modules a plugin takes over, and core using its built-in for the rest. Then `skelcrew/skelcrew-herdr` in its own repository, providing sessions, transport and status. A plugin that provides status gets every status change through `status`. Each thread remembers its host.
- **Depends on.** Phase 1 for the interface, phase 1b for the status that `status` reports, phase 4 for `sc add -g`.
- **Risky.** Typing into a session. Every trap in `docs/learnings.md` about it was learned on tmux, and a new host must honour them, the draft check above all. Recovery: an engine that starts must find agents on two hosts at once.
- **Tested.** A fake plugin, a short script that keeps sessions in a folder, runs the same tests tmux runs, once providing only sessions, with messages going through the built-in transport on its sessions, and once providing transport and status too, checking that `status` gets each change. A thread started on tmux keeps running there after the host changes. `skelcrew-herdr` is tested in its own repository.

### Phase 6: the list

- **What changes.** `sc` shows the list. Enter attaches through the session host. `m`, `y` and `n` work there. The split-screen app and its tmux server are removed, with their tests and their part of `docs/learnings.md`. The short names kept in phase 2 go.
- **Depends on.** Phase 2 for tasks and stages, phase 5 for attaching through any host.
- **Risky.** People used to the sidebar lose it. The list must reach a thread that needs you as quickly as the sidebar did: one row and Enter.
- **Tested.** The list is drawn on a tmux socket of the test's own, as the screen tests are today, with fake tasks in each stage. Attaching and detaching return to the same row. A merge and a start each ask first.

## Open questions

Each has the answer this document assumes until someone decides otherwise.

1. **Richer flows.** Later, once real use shows what is needed: custom stages, several reviewers, skipping stages, and picking a flow by label or rule. Assumed for v6: the one built-in `default` flow, other flow files only as the lead picks them, and no flow language.
2. **Which format do skills use?** Assumed: Claude Code's `SKILL.md` folders, copied where each harness looks, in a folder of one session's own, and listed in the instructions for a harness that reads none. If a shared format for skills settles across harnesses, Skelcrew follows it.
3. **One PR per task?** Assumed: yes. A task across repositories, with a PR in each, would come with projects, as the spec's list of what isn't in this version describes.
4. **Does every open issue appear as a task?** Assumed: yes, in stage `issue`, as every open issue shows in today's list. A repository with hundreds of open issues may need a filter, such as only issues with a label, which would be a setting in `skelcrew.yaml`.
5. **Should reviewers become threads?** Assumed: not in v6. They stay fresh one-off runs, and **Reviewers** says how a flow could keep one.
6. **How does herdr group repositories?** herdr-core has no workspaces. Assumed: Skelcrew labels each session with its repository, task and role, and herdr's app groups by the repository label. If herdr adds workspaces, the plugin maps a repository onto one.
7. **How is the background engine stopped?** Assumed: with systemd or launchd's own commands, and no `sc` command of its own, since agents keep running either way.
8. **Should a host's own messaging between agents, such as herdr's, carry builders' reports to the lead?** Assumed: not in v6. A plugin could provide it later, with the messages module still deciding who may talk to whom. Nothing depends on it.
9. **What does a Rex plugin provide?** Assumed: sessions, and status if Rex accepts reports, with messages on the built-in transport. This is from Rex's public pages only, and is checked once Rex has an API.
10. **How does status reach herdr?** Assumed: a relay of the plugin's own in each pane writes OSC 7501, since only the program in a pane can. If herdr-core takes status over its API, the relay goes.
11. **Should the issue show its task's stage as a label?** Assumed: not in v6. The issue shows only today's signals: the claim, the assignee and the closing PR. A label such as `skelcrew: ready for review` would show progress on GitHub, at the cost of label churn on every stage change.
