# Skelcrew v6: the migration

Nov 18, 2026 · the plan that takes Skelcrew to the design in `docs/spec.md`

`docs/spec.md` describes Skelcrew as v6 intends it. This document says only how the code gets there: the phases, their order, what each depends on, and where the risk is. Phase PRs implement the spec. They never edit it. If the spec and the code a phase needs disagree, the builder stops and reports it.

No rewrite. Each phase lands as small pull requests that pass `bun run check`, merges on its own, and leaves Skelcrew working for every thread already running.

## What goes away

Each phase that replaces something removes the old code, its tests and its part of `docs/learnings.md` in the same pull requests.

- **The split-screen app**, in phase 6: the sidebar and its rows, the tabs, the header and the strip, the footer's keys, the lists of issues, PRs and threads, the issue and PR pages, the list of keys, the copying through two tmux servers, and the screen's own tmux server. That is most of `src/screen/`, and most of the traps under **The screen** in `docs/learnings.md`. `sc show` and the PR on its forge take the place of the pages.
- **`sc serve`**, replaced by `sc up` in phase 4.
- **`sc plugin …`**, replaced by `sc add`, `sc remove`, `sc update`, `sc setup` and `sc plugins` in phase 4.
- **`sc remote add` and the copying of your setup before every `sc --remote`**, with `src/machine/copy-setup.ts` and the comparison that decides what changed, replaced by `sc --remote <host> install` in phase 4.
- **The first run**, which becomes `sc install` in phase 4.
- **`sc issue ls`, `sc issue show` and `sc pr show`**, kept as short names for `sc ls` and `sc show` from phase 2 until phase 6.

## Phases

### Phase 0: clear the decks

- **What changes.** Before phase 1 starts, the open pipeline PRs are finished and merged, as v6 builds on each of them:
  - **#280**, messages: they wait in the database, in order, are never dropped silently, drop stale event messages when a new round starts, and bring a note to the lead after 10 minutes. It becomes the first version of the messages module.
  - **#262**, harness usage limits and review timeouts. This is engine behaviour, which v6 keeps.
  - **#278**, the full suite once per commit. This is flow behaviour, which the default flow keeps.
  - **#261**, `sc peek` and `sc interrupt`. Phase 1 moves them onto the sessions module's `read` and `interrupt`.
  - **#373**, merge when ready: `sc merge --when-ready` and `--cancel`, the armed plan kept in the database, the merge at the approved commit, the record posted before it, and what keeps a plan armed or disarms it. Phase 2 moves the plan onto the task, and phase 6 shows it in the list.

  Work on the split-screen screen stays parked, since phase 6 removes it: #265, #266, #268, #274, #276 and the work on the sidebar's order. Only a fix for something broken lands there.

  The earlier issues for a session interface (#283) and a session plugin job (#284) are replaced by phase 1's base modules and phase 5's runtime plugins. They are rewritten as issues from the spec and this plan.
- **Depends on.** Nothing.
- **Risky.** Nothing new: each PR is reviewed and merged on its own, as today.
- **Tested.** By each PR's own tests.

### Phase 1: the base modules

- **What changes.** The five base modules are created, each with its built-in: sessions on tmux, with `sc peek` and `sc interrupt` from #261 moved onto `read` and `interrupt`, the built-in transport on top of them, the messages module, which takes over #280's queue and rules unchanged, the sandbox as it is, and the built-in status, which does exactly what today's code does with the hooks it has today. Nothing changes in behaviour: the messages module keeps #280's rules exactly, and the status module keeps today's hooks and screen reads. The settings are read by one loader, which merges built-in defaults, the repository's `skelcrew.yaml` and your `config.yaml` in the order the spec's **Which wins** gives. The roles' instructions move from `src/agents/prompts/` and the reviewer's code into built-in default files, in the same shape as `.agents/`, and are read from there.
- **Depends on.** Phase 0.
- **Risky.** The messages module touches every message an agent gets, so a mistake there loses or repeats one. Sessions and transport have one implementation each until phase 5. That goes against "no abstraction before the second use", and is accepted because the second use is planned, and because the seam lets phases 2 to 4 be written without tmux in mind. Each module is plain functions in a file of its own, with no class or factory.
- **Tested.** Every existing test passes unchanged, which is the proof that nothing changed. New tests check the loader's order with fake files, that the built-in files give the same instructions the code gave, each rule of the messages module against a fake transport (who may send to whom, order, waiting until idle, refusals, the note to the lead after 10 minutes, dropping a stale event message), carried over from #280's tests.

### Phase 1b: status from hooks

- **What changes.** The built-in status grows to what the spec's **Status** describes. Agent state is kept on the thread, from hooks and from the screen where no hook fires. The lead gets the same hooks as builders. Codex builders get the `Interrupt` hook, so a Codex builder stopped with Esc shows `idle` rather than `working`. This is a deliberate change in behaviour, kept apart from phase 1 so that phase 1 stays a pure seam.
- **Depends on.** Phase 1, for the status module.
- **Risky.** A wrong state could hold a message back or type into a busy agent. So the transport's screen check before typing stays, whatever the state says.
- **Tested.** Each row of the status table, with a fake harness that runs the hooks, plus the two screen gaps: Esc on Claude Code and an error on Codex. A test checks that the lead's hooks change its state and flag nothing.

### Phase 2: tasks

- **What changes.** A database migration adds a tasks table. Every existing thread becomes a task with one builder thread, keeping its name, folder, branch, session and PR. The task takes the title, body, short title, updates, PR, checks, rounds, review state, assignment and armed merge when ready. The thread keeps its role, harness, session, status and needs you. Commands take task names, and `task/role`. Open issues show as tasks in stage `issue`. `sc ls` and `sc show` arrive, and `sc issue ls`, `sc issue show` and `sc pr show` become short names for them until phase 6. The tracker works as a source and a mirror, as the spec's **The tracker is a source and a mirror** says: open issues show as tasks, the label starts one, and claiming, assigning and closing on merge work as today, with the task's data stored on the task.
- **Depends on.** Phase 1.
- **Risky.** The database migration, on machines with threads running. It only adds: new tables and columns, filled from the old ones, which stay and are no longer read, as the `open_items` table did. So only one daemon may use the database across the migration. It runs when the new release's daemon starts, and one daemon per machine already means that happens only once the old one has stopped. Agents keep running in their sessions meanwhile, as through any update. After the migration, nothing of the old release writes to the database: its daemon has gone, and an old screen still open only reads. Running the old release again afterwards is not supported, since what it wrote would go into columns the new code ignores. The way back is the copy of `skelcrew.db` Skelcrew makes beside it before migrating. The migration runs once, inside one transaction.
- **Tested.** Database files saved from the current release, with threads in every status, are migrated in tests. Each command then shows the same threads under the same names. A test checks that the new daemon refuses to start, and so to migrate, while another daemon holds the socket. Another checks that a thread's rounds, PR, review, updates and armed merge when ready written just before the migration show up on its task after it, and that the armed plan still merges, cancels and disarms as before. A fake tracker and forge check that an open issue shows as a task in stage `issue`, that a label starts it, and that claiming, assigning and closing on merge happen as today.

### Phase 3: configuration as files

- **What changes.** `sc init` writes the files, with no detection. Skelcrew reads `.agents/` and the new `skelcrew.yaml` from its clone of the default branch. The built-in `default` flow, read from its file, replaces the hard-coded loop and gives today's behaviour. The lead's instructions gain flow triage: in a repository with other flow files, it picks the flow with `sc start --flow` and tells you whenever it isn't `default`. Skills are copied in for each session, into a folder of that session's own. Trust for `.agents/` arrives with `sc repo trust`. Per-repository overrides under `repos:` in your `config.yaml` arrive, at the top of the order the spec's **Which wins** gives, and the loader from phase 1 gains that layer. A repository you only drop into, with no `skelcrew.yaml` to commit, can then get its setup and test there instead, and the lead offers that. `limits.threads` arrives: a repository's `skelcrew.yaml` can limit how many builders run at once, and a start over the limit waits in a queue of tasks, shown as `queued` under Working. Today's settings keep working, in their old shape, alongside the new one. In a repository's `skelcrew.yaml`, `lead:`, `builder:` and `reviewer:` are read as the roles' harness and model until it has role files, and `max_rounds` is read as the default flow's `rounds` until it has a flow file. In your `config.yaml`, `lead:`, `builder:` and `reviewer:` are read as `roles:`, and `max_rounds` as your default for `rounds`. Where both shapes say something, the new one wins. `sc` says once which old key it read and what replaces it, and changes no file itself.
- **Depends on.** Phases 1 and 2.
- **Risky.** Trust. A mistake here lets a repository's files run something you didn't approve. So the checks are tested first, and an `.agents/` that isn't approved never runs. The queue of tasks under `limits.threads` is new state: a task must never be lost from it or started twice, across a restart of the engine, a claim by another machine, or `sc rm`. And `repos:` must override only the repository it names.
- **Tested.** The queue: a start over `limits.threads` waits and shows `queued`, starts in order when a builder ends, keeps its place after a restart of the engine, and leaves the queue on `sc rm`, back to `issue`. A labelled issue in the queue is claimed once. `repos:` overrides beat the repository's files for that repository only. Repositories in temporary folders with and without each file, and with today's settings in their old shape, such as `max_rounds: 5`, which must still give five rounds, checking the order of settings, that a changed `.agents/` makes the repository need you while new tasks still start on the version you approved, until `sc repo trust` approves the new one, that no file can set what is yours, that `sc init` writes setup and test only as commented examples, and that `sc init` in a checkout with an `.agents/` changes none of its files and asks before approving it. The flow's settings are tested through the pure code that decides what an event means, with no clock, files or network. A test checks that a task from a label gets `default`, that `--flow` names another flow file of the repository, that `sc start <task> --flow` switches the flow of a task whose builder hasn't submitted yet, and that it refuses once the builder has.

### Phase 4: the npm-style lifecycle

- **What changes.** `sc install`, `sc add`, `sc remove`, `sc update`, `sc setup` and `sc plugins`, with `skelcrew.lock` and your own lock. The first run becomes `sc install`. `sc up` and `sc up --bg` replace `sc serve` and the service install. `sc --remote <host> install` replaces `sc remote add` and the copying of your setup, and `sc --remote <host> up --bg` runs the engine there. `src/machine/copy-setup.ts` and the setup comparison in `--remote` go. The manifest's `kind:` and `provides:` replace `jobs:`, which is still read, and the GitHub plugin's manifest says `kind: io`. The GitHub plugin is declared in `skelcrew.yaml`, pinned in `skelcrew.lock` and installed by `sc install`, as the spec's **I/O plugins** says. Saying yes to the GitHub plugin in a GitHub checkout adds it as yours, as `sc add -g` does.
- **Depends on.** Phase 3, for `plugins:` in `skelcrew.yaml`.
- **Risky.** Trust again: every path that installs a plugin must ask. Moving machines that run today's setup: their installed plugins are written into your lock as they are, so nothing is reinstalled and nothing is asked again. A server set up by `sc remote add` must keep working: its setup is already there, so its first `sc --remote <host> install` changes nothing.
- **Tested.** Fake plugins in local git repositories with version tags, never GitHub. `sc install` run twice changes nothing the second time. A changed commit in the lock asks again. Without a terminal, nothing installs. `--remote` is tested against a fake `ssh`, as today, including `install` on a server set up the old way.

### Phase 5: runtime plugins

- **What changes.** Runtime plugins, with `provides:` naming the base modules a plugin takes over, and core using its built-in for the rest. Then `skelcrew/skelcrew-herdr` in its own repository, providing sessions, transport and status. A plugin that provides status gets every status change through `status`. Each thread remembers its host.
- **Depends on.** Phase 1 for the interface, phase 1b for the status that `status` reports, phase 4 for `sc add -g`.
- **Risky.** Typing into a session. Every trap in `docs/learnings.md` about it was learned on tmux, and a new host must honour them, the draft check above all. Recovery: an engine that starts must find agents on two hosts at once.
- **Tested.** A fake plugin, a short script that keeps sessions in a folder, runs the same tests tmux runs, once providing only sessions, with messages going through the built-in transport on its sessions, and once providing transport and status too, checking that `status` gets each change. A thread started on tmux keeps running there after the host changes. `skelcrew-herdr` is tested in its own repository.

### Phase 6: the list

- **What changes.** `sc` shows the list, with a details pane beside it for the row you are on when the terminal is wide enough. Once the needs-you work in #468 lands, the pane also shows what the task needs from you, right after the links. Enter attaches through the session host. `m`, `y` and `n` work there, and a task's row shows its armed merge when ready and what it waits on. The split-screen app and its tmux server are removed, with their tests and their part of `docs/learnings.md`. The short names kept in phase 2 go.
- **Depends on.** Phase 2 for tasks and stages, phase 5 for attaching through any host.
- **Risky.** People used to the sidebar lose it. The list must reach a thread that needs you as quickly as the sidebar did: one row and Enter.
- **Tested.** The list is drawn on a tmux socket of the test's own, as the screen tests are today, with fake tasks in each stage. The pane follows the row you are on, and is hidden in a narrow terminal. Attaching and detaching return to the same row. A merge and a start each ask first.

### Any time: what a failed check says

- **What changes.** The GitHub plugin's `log` answer gives the failing tests and their errors, from the check run's annotations and the failed step, rather than the end of the job's log, where the cause is often far above the last lines.
- **Depends on.** Nothing. The change lives in the GitHub plugin alone, and Skelcrew still types into the builder whatever `log` returns.
- **Risky.** Nothing new.
- **Tested.** In the GitHub plugin's own repository.

### Any time: merge when ready across a restart, and docs-only PRs

- **What changes.** Two gaps in behaviour already built, fixed to match the spec's **The review** and **Merge when ready**. The record that a merge when ready was asked for carries a hidden marker with its plan and commit, `<!-- skelcrew:merge-when-ready plan=<id> commit=<sha> -->`, and is kept on the task, not only in the engine's memory. Before posting, the engine looks for that marker among the PR's reviews too. So a restart never posts it twice, even one that came after the forge took the review but before the engine saved that. A docs-only commit, whose review skips the wait for CI, is ready and may be merged only once the wait for CI's first check on it has ended, as the spec's **The wait for checks** says. Its approval makes the wait the review skipped. Today a docs-only review skips the wait and the PR can be ready before CI shows. And a PR CI never runs on, such as a docs-only one CI skips, never merges by itself: both merges wait for CI in any repository where a poll once found CI on a PR. The human had to merge #472 and #474 by hand. Once the wait ends with no check on the commit, the task keeps that no CI runs on it. Readiness, merge when ready and merge without approval then go on as for a repository with no CI, and `sc ps` and the list say `no CI`. A check that shows later still counts. The GitHub plugin keeps a review's body unchanged both ways, HTML comments included, as the forge contract says.
- **Depends on.** Phase 2, for the task that holds both.
- **Risky.** A merge that goes ahead before a required check starts. So the wait comes before both the stage and the merge.
- **Tested.** Through the pure code that decides what an event means: an armed plan whose record was posted before a restart doesn't post it again, and neither does one whose record the forge took before the engine stopped without saving it, found by its marker in the PR's reviews, and a docs-only PR with no check yet is neither ready nor merged until the wait ends. It is ready when the wait ends with no check, as when CI skips it with a paths filter while running on other PRs, or as the first review after a restart in a repository with no CI. One whose check shows during the wait goes by its result, and so does one whose check shows after it, so a late failing check stops the merge. A marker for another plan or commit doesn't count. Through the daemon with a fake forge: a PR with no check merges when ready, or without approval, once the wait ends, and `sc ps` says `no CI`.
